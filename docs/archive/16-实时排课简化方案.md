## 关键修复记录（2026-06-01 E2E 调试）

### Bug 1：Beam constructor 只放 1 个 session（最严重的 bug）
**症状**：每个教学任务只被排到 1 周。48 课时的课周次显示只有 1 周。
**根因**：`construct_timetable()` 循环每个 task 一次，枚举所有周×slot 后**只选了最佳的一个**。`total_lessons=24` 的 task 只放了一次，剩余 23 次丢失。
**修复**：把外层从"每个 task 放一次"改为"根据模板周次 + 柔性溢出，放满 total_lessons 个 session"。

### Bug 2：time_slot_id 硬编码
**症状**：`fk_allocation_item_time_slot` 外键冲突。
**根因**：`BeamState.add()` 用公式 `1001 + (week-1)*25 + (day-1)*5 + (period-1)` 算 ID，和 DB 自增 ID 对不上。
**修复**：传 `slot_index` 查真实 DB ID，找不到回退公式。

### Bug 3：周次分布压缩到 10 周
**症状**：18 周的学期，所有 session 被塞进前 6-10 周。
**根因**：
1. `template_generator` 评分公式 `compactness * 0.4` 偏向紧凑（用更少周次）
2. `span_penalty` 公式 `min(0, -0.01*(span - 2*lessons))` 对正常课时永远返回 0，形同虚设
3. 内层放置逻辑每轮放 `max_per_week` 个 session，超过 `candidate_weeks` 分配的额度
**修复**：
- 放弃模板生成器的紧凑周次分布，改为 beam constructor 内主动按学期长度均匀分布
- 算法：先给 18 周各 1 个 session，余下的从学期末尾开始追加（不超过 `max_per_week`）
- 每轮只放 1 个 session（`candidate_weeks` 已包含每个 session 的独立条目）

### Bug 4：getMaxWeeklyHours() 编译报错
**症状**：`mvn clean compile` 失败。
**根因**：`max_weekly_hours` 已从 schema/entity 移除，但 `AllocationSchemeConflictDetector.detectWorkloadViolations()` 还引用。
**修复**：检测到字段不存在时跳过工作量检查，log 记录"暂不检测"。

### Bug 5：AllocationTaskController 泛型不匹配
**症状**：编译失败。
**根因**：`ApiResponse.error()` 返回 `ApiResponse<Void>`，但方法签名需要 `ApiResponse<Map<String, Object>>`。
**修复**：`@SuppressWarnings("unchecked")` 转型。

### Bug 6：前端 restoreRunningGeneration 不认 COMPLETED
**症状**：E2E 生成完成后端白了，但前端进度条还卡在"检测方案冲突 1/1"。
**根因**：`restoreRunningGeneration()` 只处理 `isRunningGeneration(status) === true`（即 RUNNING 状态），COMPLETED 被 `continue` 跳过。
**修复**：加 `status?.status === "COMPLETED"` 分支，直接 `applyGenerationStatus` 不启动 SSE。

### Bug 7：SSE emitter.send() 阻塞
**症状**：Java 后端冲突检测日志停在了 classroom-time，后续全部卡死。
**根因**：`GenerationTracker` 的 `newSingleThreadExecutor()` 内调用 `emitter.send()`，当前端 SSE buffer 满时 `send()` 阻塞整个线程。
**修复**：`sendStatus` 改为 `CompletableFuture.runAsync` 异步发送 + 5 秒超时 `future.get(5, TimeUnit.SECONDS)`。

## 剩余问题

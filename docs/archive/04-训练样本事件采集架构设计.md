# 训练样本事件采集架构设计

> ⚠️ **V3 更新 (2026-06-02)**: 本文档描述的事件采集架构（`ml_feedback_event` → 样本构建 → 模型重训）方法论仍然有效，但下游消费者已从 V2 的"片段级 GA 评分器"变为 V3 的"Placement Model"。事件类型定义、快照结构、看板设计不变；样本构建器的输出格式需适配 V3 的多分类训练数据格式。详见 [17-V3-CP-SAT排课架构设计](./17-V3-CP-SAT排课架构设计.md)。
>

当前阶段暂缓实现模型重训。真实样本量还不足，直接做重训很难稳定体现效果，也容易把主要精力消耗在流程完整性而不是模型可验证性上。

下一阶段优先目标是让系统可靠地产生可训练数据：先把方案确认、手动调整、人工标注等行为沉淀成结构化事件，再基于事件覆盖情况决定何时进入样本构建和模型重训。

## 核心原则

- 先记录行为事实，不直接固化成 LightGBM 训练行。
- 事件表是长期资产，训练样本是可反复生成的加工产物。
- 未被选择的候选方案不等于差方案，第一版不直接作为负样本。
- 冲突、画像惩罚是状态上下文，第一版不单独作为训练事件。
- 原始事件不做相消；相消和压缩只发生在训练样本构建阶段。

## 架构分层

```text
用户/系统行为
  ↓
ml_feedback_event：记录事实 + 快照
  ↓
事件看板：统计事件量、覆盖面、标注情况
  ↓
样本构建器：压缩 ITEM_MOVED、解释标签和权重
  ↓
训练 CSV / 临时样本集
  ↓
模型重训与评估
```

第一阶段只落地到事件采集和事件看板，不做模型重训。

## 事件类型

第一版事件类型收敛为：

```text
SCHEME_CONFIRMED
ITEM_MOVED
ITEM_MARKED_GOOD
ITEM_MARKED_BAD
```

暂不做：

```text
SCHEME_REJECTED
SCHEME_REEVALUATED
ITEM_CONFLICT_DETECTED
ITEM_PROFILE_PENALIZED
```

原因：

- `SCHEME_REJECTED` 或未选候选不一定是坏方案，直接标负样本会污染偏好学习。
- 验收结果、冲突和画像惩罚更适合作为 snapshot 上下文，不适合作为独立偏好事件。
- 人工标注比自动状态更能表达真实偏好，应作为第一版重点。

## 事件表设计

第一版使用事件表，而不是最终训练样本表。建议表名：

```text
ml_feedback_event
```

建议字段：

```text
id
event_type
task_id
scheme_id
item_id
teaching_task_id
actor_type
actor_id
reason_code
reason_text
before_snapshot_json
after_snapshot_json
context_snapshot_json
created_at
```

字段职责：

- `event_type`：事件类型。
- `task_id`：分课任务 ID。
- `scheme_id`：候选方案 ID。
- `item_id`：片段级事件填写，方案级事件可为空。
- `teaching_task_id`：片段对应教学任务，便于后续按课程、教师、班级聚合。
- `actor_type`：`ADMIN`、`SYSTEM`，后续可扩展 `TEACHER`。
- `actor_id`：操作者标识，用户体系完善前可为空。
- `reason_code`：结构化原因，例如 `TEACHER_PREFERENCE`、`CLASS_BALANCE`、`ROOM_FIT`、`MANUAL_JUDGEMENT`。
- `reason_text`：用户自由填写说明。
- `before_snapshot_json`：调整前状态，主要用于 `ITEM_MOVED`。
- `after_snapshot_json`：调整后或标注时的当前片段状态。
- `context_snapshot_json`：事件发生时的方案级上下文。
- `created_at`：事件发生时间。

## Snapshot 设计

事件快照分三类：

```text
before_snapshot_json
after_snapshot_json
context_snapshot_json
```

`before_snapshot_json` 和 `after_snapshot_json` 用于片段调整事件，记录移动前后片段状态。最小结构：

```json
{
  "item": {
    "id": 888,
    "scheme_id": 12,
    "teaching_task_id": 31,
    "classroom_id": 3,
    "time_slot_id": 101,
    "valid": true,
    "conflict_message": null,
    "profile_penalty_message": null
  },
  "time_slot": {
    "week_number": 1,
    "day_of_week": 1,
    "period_index": 1
  },
  "classroom": {
    "capacity": 60,
    "classroom_type": "普通教室"

    "total_student_count": 80
  },
  "teacher_profile": {
    "has_profile": true,
    "preference_json": "{...}"

```

`context_snapshot_json` 用于所有事件，记录事件发生时的方案状态。最小结构：


## 事件解释与样本构建

事件表只记录事实，不直接给模型训练使用。训练样本构建器从事件表读取事件，并按固定规则解释成标签和权重。

事件解释优先级：

```text
人工标注 > 确认方案 > 调整行为
```

建议权重：

```text
ITEM_MARKED_GOOD      label=1, weight=2.0
ITEM_MARKED_BAD       label=0, weight=2.0
SCHEME_CONFIRMED item label=1, weight=0.8
ITEM_MOVED start      label=0, weight=1.0
ITEM_MOVED final      label=1, weight=1.2
```

如果人工标注和移动行为冲突，以人工标注为准。

## 调整事件压缩规则

`ITEM_MOVED` 原始事件全部保留；相消和压缩只发生在训练样本构建阶段。

分组规则：

```text
scheme_id + item_id
```

会话窗口：

```text
同一 scheme_id + item_id 下，相邻移动间隔 <= 10 分钟，归为同一个 adjustment session。
```

压缩规则：

- 连续移动 `A -> B -> C -> D`，训练解释为 `A -> D`。
- 中间态 `B / C` 视为探索过程，不参与训练。
- 如果最终回到原位，例如 `A -> B -> C -> A`，整组相消，不产生训练样本。
- 位置是否相同由 `time_slot_id + classroom_id` 判断。

压缩后样本解释：

```text
start_position -> label=0, weight=1.0
final_position -> 仅当无硬冲突、无画像惩罚时 label=1, weight=1.2
```

如果最终位置仍有硬冲突或画像惩罚，第一版不产 final 正样本，避免把测试拖拽或未完成调整误当偏好。

## 实现边界

第一阶段只做事件采集和事件看板，不做模型重训。

建议实现顺序：

1. 建立 `ml_feedback_event` 事件表和后端事件写入服务。
2. 在方案确认时写入 `SCHEME_CONFIRMED`。
3. 在片段移动时写入 `ITEM_MOVED`，包含移动前后快照。
4. 在前端片段详情或片段卡片上提供 `ITEM_MARKED_GOOD / ITEM_MARKED_BAD` 标注入口。
5. 在模型训练中心展示事件数量、类型分布和覆盖情况。
6. 后续再实现样本构建器，从事件表读取并按压缩规则生成训练 CSV。

## 当前实现

当前已落地第一阶段事件采集闭环：

- 数据表：`db/schema.sql` 中新增 `ml_feedback_event`，记录事件类型、任务、方案、片段、原因、前后快照和方案上下文。
- 后端服务：`MlFeedbackEventService` 统一写入 `SCHEME_CONFIRMED`、`ITEM_MOVED`、`ITEM_MARKED_GOOD`、`ITEM_MARKED_BAD`。
- 方案确认：确认候选方案时自动写入 `SCHEME_CONFIRMED`，并在 context 中保留确认反馈 ID。
- 片段调整：手动移动片段后自动写入 `ITEM_MOVED`，保留移动前和重评后的片段快照。
- 人工标注：方案详情的片段编辑弹窗提供“标为可参考 / 标为不满意”，调用 `POST /api/allocation-schemes/{schemeId}/items/{itemId}/feedback`。
- 事件看板：模型训练中心调用 `GET /api/ml/feedback/events/summary`，展示事件总数、类型分布和最近事件。
- 反馈导出：`GET /api/ml/feedback/export` 会把 `events` 一并导出，统计字段使用 `eventCount`。

尚未落地的部分：

- 样本构建器仍待升级为基于 `ml_feedback_event` 的解释器。
- `ITEM_MOVED` 的 10 分钟会话压缩、回原位相消、人工标注优先级处理仍在后续阶段实现。
- 模型重训链路暂不作为本阶段验收重点；当前重点是确认事件能稳定、可观察地沉淀下来。

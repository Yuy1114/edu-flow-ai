```bash
python3 -m unittest ml.tests.test_scheduling_core
```

```bash
python3 -m py_compile ml/scheduling/teacher_profiles.py ml/api/routers/ga.py ml/scripts/generate_scheme_ga.py
```

```bash
cd server
```

## 关键输出文件

### 生成方案输出

```text
ml/data/generated/task_{taskId}_{timestamp}/
├── schemes.jsonl
└── ga_summary.json
```

检查点：
- `schemes.jsonl` 每行一个 JSON 对象。
- 行数应该等于 `scheme_count`。
- 每个 scheme 都应该有 `items`。
- 每个 item 都应该有 `teaching_task_id/time_slot_id/classroom_id`。
- 每个教学任务展开后的实际课时数应该等于 `teaching_task.total_hours`。
- `time_slot_id` 必须来自 DB 查询结果，不能用公式推导。

### 候选池输出

最终架构要求先构造 teaching_task 级候选池，再交给 GA 搜索。

检查点：

- 每个 `teaching_task_id` 至少有 1 个候选，否则应明确报 infeasible。
- 每个候选代表该教学任务的完整排课安排，而不是单个 slot。
- 候选内所有 `time_slot_id` 都在 `allowed_weeks/allowed_weekdays/allowed_periods` 过滤后的时间域中。
- 候选内教室满足容量和类型要求。
- 教师硬不可排应在候选构建阶段过滤。

### 教师画像快照

```text
ml/data/profiles/snapshots/task_{taskId}_{timestamp}.teacher_profiles.jsonl
```

检查点：
- 一行一个教师。
- `teacher_id` 不能为空。
- `profile` 应该是 JSON object。
- `availability_matrix_json` 如果存在，应能被 Python 解析。

### GA 日志

```text
ml/logs/ga-algorithm.log
```

检查点：
- 多方案任务应该出现 `Generating GA scheme 1/N`、`2/N` 等日志。
- 如果只有 `1/N`，先检查生成配置的 `scheme_count`。

## V3 全量压测 preflight

V3 pipeline 在进入 CP-SAT 前会写出 `preflight_report.json`。该报告用于快速排除明显无解或候选不足，不证明数学可行。

重点字段：

- `task_count` / `expected_task_count`：实际进入 task plan 的任务数和绑定任务数。
- `no_candidate_task_count`：Placement 阶段未产出候选的任务数。
- `no_plan_task_count`：Template 阶段没有有效 plan 的任务数。
- `plan_count_min` / `plan_count_avg` / `plan_count_max`：每个任务的 plan 覆盖情况。
- `teacher_capacity_risk`、`class_capacity_risk`、`room_type_capacity_risk`：基础负载和房型候选容量风险。
- `risks`：汇总风险列表。

当 `no_candidate_task_count > 0` 或 `no_plan_task_count > 0` 时，pipeline 会 fail fast，错误消息会包含 report 路径。压测建议顺序是：先跑 `FEASIBILITY` 取得首个无冲突方案，再切换 `QUALITY` 或 `STRESS` 延长 CP-SAT 时间做质量优化。

## 常见问题

### 1. 多方案只生成第一套

表现：
- 前端只看到一套方案。
- SSE 很快 `completed`。

检查：
- GA Solver 是否以 `scheme_count` 为 TopK 目标，而不是找到第一套可行解就 return。
- `schemes.jsonl` 行数是否大于 1。
- `ga_summary.json` 是否是数组，而不是单个对象。

当前正确行为：

```text
构造候选池
  ↓
GA 搜索 TopK
  ↓
写 schemes.jsonl
  ↓
run() 返回
  ↓
SSE completed
```

### 2. 可用周/星期/节次没有生效

表现：
- 方案中出现了配置外的周次、星期或节次。

检查：
- `allocation_task_generation_config.allowed_weeks`
- `allowed_weekdays`
- `allowed_periods`
- Python 数据加载层中 `time_slots` 过滤结果。
- Candidate Pool Builder 是否只使用过滤后的 `time_slot_id`。
- Exporter 是否使用 DB `time_slot_id_by_coord`，而不是公式推导。

当前正确行为：
- 过滤后的 `time_slots` 决定所有候选。
- 输出 row 找不到 DB time_slot 映射时直接失败。

### 3. 教师硬不可排没有生效

表现：
- 教师画像中不可排的时间仍被排课。

检查：
- Java 是否导出了 JSONL 快照。
- ML 请求体是否包含 `teacher_profiles_jsonl`。
- JSONL 中 `teacher_id` 是否和 `teaching_task.primary_teacher_id` 一致。
- `availability_matrix_json` 中不可排是否用 `-1` 表示。
- `hard_unavailable` 的 weekday/period 是否在 1~7 / 1~5 范围内。

Python 可重点看：

```text
ml/scheduling/teacher_profiles.py
ml/scheduling_v2/candidate_pool.py
ml/scheduling_v2/fitness.py
```

### 4. 生成速度很慢

验收联调优先使用 `ML_GA_PROFILE=fast`，质量对比或正式候选生成再切到 `default` / `quality`。

当前支持的预设：

| Profile | population | generations | 适用场景 |
|---------|------------|-------------|----------|
| `fast` | 30 | 25 | 链路验收、前端展示验证、教师画像解释检查 |
| `default` | 60 | 60 | 日常候选方案生成 |
| `quality` | 100 | 100 | 质量对比、最终评估 |

也可以用环境变量覆盖单项参数：

```bash
ML_GA_PROFILE=fast
ML_GA_POPULATION_SIZE=20
ML_GA_GENERATIONS=10
ML_GA_CANDIDATE_TOP_N=20
ML_GA_MUTATION_RATE=0.2
```

生成后的 `ga_summary.json` / 前端方案详情会展示本次实际使用的 GA 参数。

速度瓶颈常见位置：
- 数据加载到候选池完成：模板枚举、教室排序、Placement Scorer 批量评分。
- 候选池完成到 Gen 1：GRASP / 多策略贪心初始化。
- Gen 1 之后：fitness 对 chromosome 展开和 O(n) 冲突检测。

优先排查：
- `scheme_count` 是否过大。
- `population_size` / `generations` 是否过高。
- 教学任务数量是否明显增加。
- 候选 slot 和候选 classroom 是否过宽。

后续优化方向：
- 缓存候选池和候选展开结果。
- 缓存 candidate-level penalty 和 placement score。
- fitness 使用增量冲突统计。
- LightGBM 批量预测。
- 方案之间复用部分初始化结果。

### 5. Java 解析不到 schemes.jsonl

表现：
- Python 生成成功，但 Java 报“未生成 schemes.jsonl”。

检查：
- SSE completed 中的 `output_dir` 是否指向具体任务目录。
- `AllocationMlSchemeService.parseGeneratedSchemes` 是否读取 `{output_dir}/schemes.jsonl`。
- Python 是否返回了 `out` 而不是 `out.parent`。

当前正确返回：

```json
{"output_dir": "ml/data/generated/task_14_20260525123000123"}
```

## 建议的回归清单

每次改排课核心链路后，至少确认：

| 检查项 | 方式 |
|--------|------|
| Python 核心测试 | `python3 -m unittest ml.tests.test_scheduling_core` |
| Java 编译 | `cd server && ./mvnw -q -DskipTests compile` |
| 多方案输出 | 检查 `schemes.jsonl` 行数是否 >= 2 |
| 候选完整性 | 抽查每个 teaching_task 的实际课时数是否等于 total_hours |
| 教师画像快照 | 检查 JSONL 文件是否生成 |
| 硬过滤 | 抽查输出 row 的 week/day/period 是否在配置范围内 |
| 教师 hard unavailable | 构造一个不可排时间，确认不会输出 |

## 推荐定位顺序

出现问题时，不要先看 GA 细节，建议按输入到输出排：

```text
generation_config 是否正确
  ↓
time_slots 过滤是否正确
  ↓
teacher_profiles_jsonl 是否正确
  ↓
Candidate Pool 是否为每个教学任务生成完整候选
  ↓
GA chromosome 是否只引用合法 candidate_index
  ↓
Fitness 是否能 O(n) 检出硬冲突
  ↓
Exporter 是否能映射 DB time_slot_id
  ↓
Java 是否读到正确 output_dir
```

这样通常能更快判断是输入、候选空间、搜索还是入库阶段的问题。

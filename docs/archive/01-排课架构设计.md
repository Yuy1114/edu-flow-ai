## 系统链路

```
前端生成方案请求
       ↓
Java (AllocationMlSchemeService)
  → TeacherProfileSnapshotService 导出教师画像 JSONL 快照
  → POST /api/ml/generate-scheme {task_id, teacher_profiles_jsonl}
  → GET /api/ml/generate-scheme/{task_uid}/stream（SSE）
       ↓
Python (run_ga_pipeline_by_task)
  → 接收 Java 传入 allocation_task_id
  → 读 DB: teaching_task + allocation_task_generation_config + classroom + time_slot
  → 读取 teacher_profiles_jsonl，归一化教师画像
  → 根据 config 的周次多选 / 星期多选 / 节次多选硬过滤 time_slot
  → 根据教师画像 hard_unavailable 过滤教学任务候选 slot
  → 对每个 teaching_task 枚举稳定模板集
  → 由过滤后的 time_slot 组装 availableWeeks / candidateSlotIds / DB time_slot_id 映射
  → 构建 AllocationTask
  → 按 scheme_count 循环生成 N 套方案
     → LightGBM 对 template × slot × classroom 做局部评分
     → GA 进化：模板集保持稳定，只变更 classroom / slot 选择
     → repair 处理硬冲突，LightGBM 辅助候选排序
     → 展开为 rows，time_slot_id 使用 DB 真实 id
  → 写 schemes.jsonl / ga_summary.json
  → 全部方案完成后 SSE 推送 completed/failed
       ↓
Java 收到 SSE completed 事件
  → 读 schemes.jsonl
  → 写入 allocation_scheme / allocation_item
  → 前端展示课表
```

## 核心数据模型

### 模板 (Template)

```
Template = { week_mask: int32, weeks_list: [int] }
```

- 一个模板 = **1 节课/周** × 若干生效周
- week_mask 用 int32 bitmask 表示：bit 0 = 第 1 周，bit 17 = 第 18 周
- 周重叠判断：`(a.mask & b.mask) != 0` → O(1)
- 模板的 weeks 由枚举阶段固定生成，GA **不负责调整周次**

### 模板集 (TemplateSet)

```
TemplateSet = { templates: [Template], penalty: float }
```

- 一个模板集 = 若干模板的组合
- 所有模板的 `len(weeks_list)` 之和 = 教学任务的总课次（total_lessons = total_hours / 2）
- penalty 评分维度：段数 + 均匀性 + 连续性

### 染色体 (Chromosome)

```
Chromosome = [TaskGene, TaskGene, ...]

TaskGene = {
  task_id,
  template_set_id,          // 选哪个模板集
  assignments: [
    TemplateAssignment {
      template_id,          // 模板集内的索引
      slot_id,              // 0~24 → (day, period)
      classroom_id          // 教室 ID
    }
  ]
}
```

染色体中只存 `slot + classroom`，不存周次。  
周次是模板结构的一部分，由枚举器固定生成。

### 教学任务 (AllocationTask)

```
AllocationTask = {
  task_id,
  teacher_id,
  class_group_id,            // 兼容字段：主班级 / 第一个班级
  class_group_ids,           // 合班课的全部班级
  student_count,
  total_lessons,
  available_week_mask,
  candidate_slot_ids,
  candidate_room_ids,
  template_sets
}
```

合班课冲突检测必须使用 `class_group_ids`，只看第一个班级会漏掉班级硬冲突。

### Slot 编码

```
slot = (day_of_week - 1) × 5 + (period_block - 1)
```

| slot_id | 含义 |
|---------|------|
| 0 | 周一第 1 大节（1-2 节） |
| 1 | 周一第 2 大节（3-4 节） |
| ... | ... |
| 24 | 周五第 5 大节（9-10 节） |

可用 slot 由 `availableDays × availablePeriodBlocks` 硬约束生成，不在范围内的 slot GA 不会用到。

### DB TimeSlot 映射

输出 rows 时，`time_slot_id` **不能用公式推导**，必须来自 DB 中过滤后的 `time_slot.id`：

```
time_slot_id_by_coord[(week_number, day_of_week, period_index)] = time_slot.id
```

原因：
- Java 入库只读取 `time_slot_id`，不会用 row 里的 `week_number/day_of_week/period_index` 反查。
- `time_slot.id` 是数据库自增主键，不能假设它永远等于 `(week-1)*35 + ...` 这类公式。
- 如果生成坐标不在过滤后的 time_slot 映射里，pipeline 直接失败，避免输出违反可用周/星期/节次的方案。

## 预处理阶段

### 1. 生成配置 → 硬过滤

从 `allocation_task_generation_config` 读取：

| 字段 | 过滤对象 | 约束方式 |
|------|----------|----------|
| allowed_weeks | time_slots | 只保留这些周 |
| allowed_weekdays | time_slots | 只保留这些天 |
| allowed_periods | time_slots | 只保留这些节次 |

过滤后的 time_slots 决定了：
- availableWeeks → 枚举器只从这些周生成模板
- candidateSlotIds → 只有这些 (day, period) 组合
- time_slot_id_by_coord → 输出时只允许使用过滤后 DB 真实 time_slot.id

如果过滤后没有可用时间片，或教学任务缺少候选教室 / 模板集，生成直接失败，不静默跳过任务。

### 2. 模板集枚举

`ml/scheduling/enumerator.py`

```
输入: total_lessons, available_weeks
输出: [TemplateSet, ...]

约束:
- 每模板至少 MIN_TEMPLATE_WEEKS(=2) 周
- 最多 MAX_TEMPLATES(=4) 个模板
- 最多 MAX_COMBOS(=100) 种组合
- 所有模板的 weeks 之和 = total_lessons

评分:
  penalty =
    20 × 段数
  + 10 × 可用周负载方差
  + 100 × 可用周覆盖缺口
  + 30 × 最大空洞
  + 2 × 学期中心偏移
```

枚举器不再只取 `pool[:count]`，会生成前段 / 后段 / 中段 / 均匀间隔 / 单双周式模板候选。  
每周课次方差必须把“可用但未排课”的周也算进去，否则长课时任务会被压缩到少数周，模板性会被破坏。

### 3. 教室过滤

按 `capacity >= student_count` 和 `room_type` 匹配过滤。  
GA 分配时 (slot, classroom) 联合选择，不对单一维度死定。

### 4. 多方案数量

`scheme_count` 来自 `allocation_task_generation_config.scheme_count`，Python 在同一个任务内循环生成 N 套方案：

```
# schemes.jsonl — 每行一个 JSON 对象，对应一套方案
{"items": [...]}
{"items": [...]}
...
```

全部方案写入完成后，Python SSE 才发送 `completed`。Java 读取同一个 `schemes.jsonl` 并逐个入库为多个 `allocation_scheme`。

### 5. 教师画像快照

Java 在调用 ML API 前导出本次排课任务涉及教师的画像快照：

```
ml/data/profiles/snapshots/task_{taskId}_{timestamp}.teacher_profiles.jsonl
```

调用 Python 时传入：

```json
{
  "task_id": 14,
  "teacher_profiles_jsonl": "/abs/path/ml/data/profiles/snapshots/task_14_20260525123000123.teacher_profiles.jsonl"
}
```

Python 优先使用该快照，而不是运行中再读最新教师画像，保证一次排课任务的输入可追溯。

当前已消费的画像字段：

| 字段 | 作用 |
|------|------|
| availability_matrix_json | 值为 -1 的格子转为 hard_unavailable |
| hard_unavailable / hardUnavailable | 硬不可排，直接过滤 candidate_slot_ids |
| soft_avoid / softAvoid / avoidSlots | 软避让，进入 penalty |
| avoidFirstPeriod / avoidLastPeriod | 转为 avoid_periods |
| preferredWeekdays | 未命中时加软惩罚 |
| preferCompactSchedule | 分散排课时加软惩罚 |
| preferredMaxWeeklyHours | 超过教师偏好周课次时加软惩罚 |

## LightGBM 局部评分器

LightGBM 不替代硬约束，只作为 `template × slot × classroom` 的局部质量评分器。

### 职责边界

| 模块 | 负责内容 | 是否可覆盖硬规则 |
|------|----------|------------------|
| 硬规则 | 教师 / 班级 / 教室同一周同一 slot 冲突、课次数、config 范围 | 是，必须精确执行 |
| LightGBM | 老师偏好、历史接受度、时间舒适度、教室与课程匹配度 | 否，只能辅助排序 |
| GA | 在稳定模板集上搜索全局最优 slot/classroom 组合 | 否，必须服从硬规则 |

### 评分对象

LightGBM 对 `TemplateAssignment` 级别打分，而不是对完整方案直接打分：

```
score(task, template, slot, classroom)
```

其中：
- `task` 提供课程、教师、班级、人数、房间类型等上下文
- `template` 提供 weeks_list / week_mask / 覆盖周数等结构信息
- `slot` 提供星期、节次、是否晚课等时间特征
- `classroom` 提供容量、类型、校区等空间特征

### 使用位置

| 阶段 | 使用方式 | 原则 |
|------|----------|------|
| 初始化 | 对候选 `(slot, classroom)` 批量评分，从 top-k 中采样 | 提高初始种群质量，同时保留多样性 |
| repair | 对替代候选评分，用于 delta penalty 相近时排序 | 硬冲突消除优先于模型分数 |
| fitness | 累计 assignment 级别的 ml_score，作为软质量项 | 必须弱于硬冲突权重 |

### 综合评分

```
total_penalty = hard_penalty + rule_penalty - ml_score_weight × ml_score
```

权重优先级：

```
hard_conflict: 1_000_000
rule_penalty: 10 ~ 1000
ml_score: 0 ~ 100
```

同一个 `(task_id, template_signature, slot_id, classroom_id)` 的预测结果需要缓存，避免 GA 每代重复调用模型。

## GA 阶段

### 初始化：MRV + LightGBM top-k

按约束紧度排序优先分配：
1. 周数最长的模板（最难放）
2. 总课次最多的任务
3. 学生数最多的任务（大教室需求）

分配时枚举 `(slot, classroom)` 候选：
1. 先计算真实硬资源冲突 / 规则 penalty
2. 再批量调用 LightGBM 预测局部质量分
3. 按综合评分排序
4. 从 top-k 中随机采样，避免初始种群过早收敛

初始化阶段的占用索引是：
- `(teacher_id, week, slot_id)`
- `(class_group_id, week, slot_id)`
- `(classroom_id, week, slot_id)`

不能使用全局 `(week, slot_id)` 判断冲突；不同教师、不同班级、不同教室可以在同一时间并行上课。

### 适应度函数

fitness 展开整个 chromosome 后做全局评价。硬冲突仍由规则精确判断，LightGBM 只提供软质量加分。

分层 penalty：

| 类型 | 权重 | 说明 |
|------|------|------|
| 教师冲突 | 1,000,000 | 同一教师同一 slot 同一周 |
| 班级冲突 | 1,000,000 | 任一 class_group_id 同一 slot 同一周 |
| 教室冲突 | 1,000,000 | 同一教室同一 slot 同一周 |
| 缺失教学任务 | 1,000,000 | 每个 task 必须进入 chromosome |
| 缺失模板 assignment | 1,000,000 | 每个模板必须有 slot/classroom |
| 同一天重复课 | 100 | 同一教学任务多模板排同一天 |
| 模板集 penalty | 见评分 | 段数 + 均匀性 + 连续性 |
| 晚课 | 30 | period_block ≥ 4 |
| LightGBM quality | 软加分 | assignment 级别预测分，不能抵消硬冲突 |

### 交叉：Task-level Uniform

```
for each task:
    child.task_gene = parentA or parentB (各 50% 概率)
```

不按模板交叉（同一 task 的模板强相关，交叉会导致 repair 爆炸）。

### 冲突检测

三种硬约束（权重 1,000,000）：

| 类型 | 条件 | 说明 |
|------|------|------|
| 教师冲突 | 同一教师、同一 slot、周重叠 | `teacher_id` + `slot_id` + weekMask |
| 班级冲突 | 任一班级重叠、同一 slot、周重叠 | `class_group_ids` + `slot_id` + weekMask |
| 教室冲突 | 同一教室、同一 slot、周重叠 | `classroom_id` + `slot_id` + weekMask |

最终输出前还会校验：
- `missing_task_count == 0`
- `hard_conflicts == 0`
- 每个输出 row 的 `(week, day, period)` 都能映射到过滤后的 DB `time_slot.id`

### 变异

模板集一旦进入个体后保持稳定，GA 不再变更 `template_set_id`。  
变异只允许调整模板绑定的资源选择：

- 换 slot — 重新从 candidateSlotIds 选
- 换 classroom — 重新从 candidateRoomIds 选
- Swap 两个模板的 slot（同一 task 内）

### 修复

repair 作为主要优化器，GA 作为扰动器。  
发现冲突 → 生成替代 slot/classroom → 先按硬冲突过滤 → 再用规则 penalty + LightGBM score 排序。

修复优先级：
- 教师冲突 / 班级冲突：优先换 slot
- 教室冲突：优先换 classroom，不行再换 slot
- delta penalty 接近时，选择 LightGBM 分数更高的候选

限制 `MAX_REPAIR_ATTEMPTS = 30`，避免死循环。

### 精英保留

每代保留 top N（默认 5）。

## 验证覆盖

核心测试位于 `ml/tests/test_scheduling_core.py`：

- 模板枚举包含非前缀周次模式
- 课次超过可用周时优先覆盖全部可用周
- 不同硬资源的课程允许同一时间并行
- 缺失教学任务会被 fitness 惩罚
- 合班课任一班级重叠都会触发班级冲突
- 输出 rows 使用 DB `time_slot_id` 映射，而不是公式推导

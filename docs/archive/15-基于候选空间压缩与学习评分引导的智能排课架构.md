## 一句话定义

> **模型负责生成高质量候选集，GA 负责在候选集里组合全校无冲突课表，
> 教师画像和影响因子通过 fitness 真正影响方案生成。**

论文题目建议：

> **基于学习引导候选空间压缩与遗传搜索优化的高校智能排课系统设计与实现**

## 核心原则

1. Java 后端只传 `allocation_task_id`，不在请求体里展开排课数据。
2. Python 排课服务是生成决策中心，负责加载数据、构造候选、搜索方案和导出结果。
3. 学习模型不直接生成最终课表，当前主职责是根据 `teaching_task` 推荐教室候选；
   时间 slot 由规则、教师画像和覆盖采样生成，不做 `task × template × slot × room` 逐点评分。
4. GA 不在原始 `time_slot × classroom` 空间盲搜，而是在每个教学任务的候选集空间内搜索。
   但候选集不能只保留局部最高分 TopN，必须保留时间、教室和模板覆盖性，避免把全局可行解提前剪掉。
5. `gene = candidate_index`，每个 gene 选择一个教学任务的完整排课候选。
6. 硬约束必须由 O(n) 冲突检测兜底，不能交给模型判断。
7. `scheme_count` 是生成目标，不是展示参数；求解器必须产出指定数量的 TopK 方案或明确失败。
8. 人工调课和确认结果进入反馈数据集，用于后续教室排序模型训练。

## 模块职责

| 模块 | 输入 | 输出 | 职责 |
|------|------|------|------|
| `allocation_task` | 用户配置 | `task_id`、时间域、权重、方案数 | 作为一次排课任务的配置事实源 |
| Python 数据加载层 | `allocation_task_id` | 教学任务、教室、时间段、教师画像、生成配置 | 从 DB 读取完整排课上下文 |
| Template Generator | 教学任务课时、可用周次 | TopK 周稳定模板 | 预制课时分布模式，避免逐周随机搜索 |
| Room Ranker | 教学任务、教室库 | TopN 教室候选 | 根据 `teaching_task` 推荐教室，压缩教室空间 |
| Slot Coverage Builder | 模板、时间域、教师画像 | day/period 候选 | 用规则和覆盖采样生成时间候选，不调用模型逐点评分 |
| Candidate Pool Builder | 模板、推荐教室、时间域 | 每个任务动态数量候选 | 生成完整 task-level 候选集，并保留覆盖型兜底候选 |
| GA 初始化种群 | 候选集 | 初始 chromosome 集合 | GRASP、多策略贪心和随机初始化混合 |
| GA Solver | 候选集、初始种群 | TopK chromosome | 在候选索引空间做全局组合优化 |
| Fitness | chromosome、配置、画像 | 可行性和质量分 | 硬约束 veto + 软约束排序 |
| Exporter | TopK chromosome | `schemes.jsonl`、`ga_summary.json` | 展开为 Java 可入库的方案结果 |
| 人工调课系统 | 候选方案 | 调整记录、确认反馈 | 形成训练样本和画像演进依据 |

## 候选集设计

候选集是本架构的核心边界。候选粒度必须是一个教学任务的完整排课安排，
而不是单个 `(task, room, slot)`。

```text
TaskCandidate {
  teaching_task_id
  candidate_index
  assignments: [
    {week_number, day_of_week, period_index, time_slot_id, classroom_id},
    ...
  ]
  template_signature
  room_ids
  room_rank_score
  teacher_profile_penalty
  influence_factor_score
  metadata
}
```

候选池设计采用 **质量优先 + 覆盖兜底 + 动态扩容**，而不是固定截取
`TopN room × TopN day/period`。原因是全校排课存在几千个教学任务时，局部高分候选
往往集中在相同热门时间段和热门教室；候选集过窄会使 GA 的染色体空间先天不存在
无冲突组合。

### 候选池分层

每个教学任务维护逻辑上的两层候选：

```text
primary candidates:
  局部分数高、满足基础覆盖的候选，供 GA 常规搜索

fallback candidates:
  分数可能略低，但覆盖更多 day/period 和教室，用于冲突定向变异和修复
```

实现上可以仍使用一个 `candidate_pool[i]` 列表，通过 `candidate.metadata.tier`
区分候选层级。`fallback` 候选只施加轻微质量惩罚，不能作为硬过滤条件。

### 动态候选规模

候选池大小按任务难度动态调整：

```text
difficulty =
  total_lessons
  + class_group_count
  + required_room_type scarcity
  + allowed_slot scarcity
  + teacher/class_group load
```

建议默认范围：

| 任务类型 | room 候选 | day/period 覆盖 | candidate 数 |
|----------|-----------|-----------------|--------------|
| easy | 8 | 12-16 | 60-80 |
| normal | 15 | 20-30 | 120-150 |
| hard | 25 | 40-60 | 240-300 |
| critical | 40 | 全 allowed day/period | 500+ |

当允许 day/period 总量本身较小，例如周一到周五第 1-4 节只有 20 个组合时，
hard/critical 任务应尽量覆盖全部 day/period，而不是只取模型分最高的几个时间。

### 教室候选覆盖

教室候选不能只按分数取前几个，应分桶合并：

```text
room_candidates =
  bound_room_bucket
  + exact_type_bucket
  + near_capacity_bucket
  + overflow_capacity_bucket
  + diversity_bucket
```

绑定教室和类型匹配教室优先，但仍要保留若干容量更大或通用教室作为兜底，避免稀缺
教室在全局组合中成为不可恢复冲突点。

### day/period 覆盖

时间候选由三路合并：

```text
slot_candidates =
  rule_top_slots
  + weekday/period coverage_slots
  + low_pressure_or_rotated_slots
```

候选构建至少保证：

- 每个可用星期尽量保留若干 period。
- 每个可用 period 尽量跨多个 weekday。
- 热门时间保留高分候选，冷门时间保留兜底候选。
- 教师硬不可排时间仍必须过滤。

这样 GA 初始种群、变异和 repair 才有机会从冲突高峰区跳到低压力区域。

例如一门 48 学时课程，候选应表达完整课时：

```text
candidate_0:
  第1-16周，每周周二第3-4节，room A

candidate_1:
  第1-12周，每周两次，周一第1-2节 + 周四第3-4节，room B
```

这样 GA 的编码才能保持稳定：

```text
chromosome = [
  task_1 -> candidate_3,
  task_2 -> candidate_17,
  task_3 -> candidate_8,
  ...
]
```

## GA 编码

### 基因

```text
gene_i = candidate_index
```

第 `i` 个基因对应第 `i` 个教学任务，从该任务的候选池中选择一个候选。

### 染色体

```text
chromosome = int[num_teaching_tasks]
```

染色体展开后是一张完整课表。对 4000+ 教学任务场景，染色体长度就是任务数；
每个基因只在小规模候选池内取值，因此搜索空间被候选生成阶段显著压缩。

### 交叉

交叉以教学任务为单位交换候选索引：

```text
child[i] = parent_a[i] or parent_b[i]
```

不拆分单个教学任务内部的周次和课时片段，避免破坏课时完整性。

### 变异

变异只替换当前任务的候选索引：

```text
gene_i = random(candidate_pool[i])
```

可以按冲突热度做定向变异：优先变异出现在教师、班级、教室冲突中的任务。

## Fitness 分层

fitness 分为硬约束和软评分两条管线。硬约束决定是否可行，软评分决定可行方案的排序。

### 硬约束

硬约束采用 O(n) 哈希检测：

| 约束 | 检测键 |
|------|--------|
| 教师同时间冲突 | `(teacher_id, time_slot_id)` |
| 班级同时间冲突 | `(class_group_id, time_slot_id)` |
| 教室同时间冲突 | `(classroom_id, time_slot_id)` |
| 课时数不匹配 | `expected_hours == actual_hours` |
| 超出 allowed 时间域 | `time_slot_id in allowed_time_slot_set` |
| 教师硬不可排 | `(teacher_id, day_of_week, period_index)` |
| 教室容量/类型不满足 | candidate 构建阶段过滤，fitness 二次校验 |

硬约束冲突不靠模型修正。存在硬冲突的方案可以保留在进化过程中，但必须在选择时
劣于无硬冲突方案。

### 软评分

```text
quality_score =
  room_rank_weight * sum(candidate.room_rank_score)
  - teacher_profile_weight * teacher_profile_penalty
  - influence_factor_weight * influence_factor_penalty
  - balance_weight * timetable_balance_penalty
  - room_waste_weight * capacity_waste_penalty
```

软评分来源：

- Room Ranker 教室推荐分。
- 教师画像软偏好，例如早晚课、连续授课、集中/分散排课。
- 任务生成配置中的影响因子。
- 班级日负载、教师日负载、教室容量浪费。
- 方案多样性约束，避免 TopK 方案高度重复。

### 选择规则

采用可行性优先：

1. 无硬冲突方案优于有硬冲突方案。
2. 都有硬冲突时，硬冲突数少者优先。
3. 硬冲突数相同或均为 0 时，软评分高者优先。
4. TopK 输出需要保留方案多样性，避免只是同一方案的微小扰动。

## 数据流与接口

Java 调用 Python 时只传：

```json
{
  "task_id": 123
}
```

Python 数据加载层负责读取：

- `allocation_task`
- `allocation_task_generation_config`
- `allocation_task_teaching_task`
- `teaching_task`
- `teaching_task_class_group`
- `teacher`
- `teacher_profile`
- `classroom`
- `time_slot`

Python 输出保持 Java 兼容：

```text
ml/data/generated/task_{taskId}_{timestamp}/
├── schemes.jsonl
└── ga_summary.json
```

`schemes.jsonl` 每行一个方案：

```json
{
  "items": [
    {
      "teaching_task_id": 1,
      "time_slot_id": 100,
      "classroom_id": 20,
      "week_number": 1,
      "day_of_week": 1,
      "period_index": 2,
      "candidate_index": 3,
      "room_rank_score": 0.83
    }
  ]
}
```

`time_slot_id` 必须来自 DB 查询结果，禁止用公式推导。

## 推荐代码结构

```text
ml/scheduling_v2/
├── data_loader.py          # 读取 allocation_task 及排课上下文
├── template_generator.py   # 周稳定模板生成
├── room_ranker.py          # 教室候选排序
├── slot_coverage.py        # day/period 覆盖采样与规则评分
├── candidate_pool.py       # task-level 候选池构建
├── chromosome.py           # 编码、展开、方案签名
├── fitness.py              # O(n) 硬约束检测 + 软评分
├── ga_solver.py            # 初始化、选择、交叉、变异、终止
├── exporter.py             # schemes.jsonl / ga_summary.json
└── pipeline.py             # 对外编排入口
```

旧 `ml/channels` 中的 Beam Search 代码只能作为候选生成和评分模块的素材，不再作为最终求解器。
旧 `ml/scheduling` 中的 GA 代码可复用选择、参数、日志和部分 fitness 思路，但编码需要改为
`candidate_index`。

## 与旧架构的区别

| 维度 | 旧 GA 主线 | V2 Beam Search | 最终架构 |
|------|------------|----------------|----------|
| 模型角色 | 局部评分辅助 | 构造过程主引导 | 教学任务到教室候选排序 |
| 搜索空间 | 原始 slot/room 空间 | 逐步构造局部课表 | task-level 候选索引空间 |
| GA 角色 | 直接搜索 slot/room | 局部修复工具 | 全校组合优化主引擎 |
| 候选粒度 | 模板 + slot + room | 单次放置 | 完整教学任务排课候选 |
| 多方案 | GA 循环生成 | V2 当前固定 1 套 | GA TopK 满足 `scheme_count` |
| 硬约束 | fitness/repair | 构造过滤 + 修复 | O(n) fitness veto + 二次校验 |
| 论文定位 | LightGBM + GA | 候选压缩 + Beam | 学习引导候选空间压缩 + 遗传搜索优化 |

## 迁移计划

### 第一阶段：文档与接口冻结

- 以本文档作为最终架构设计。
- Java → Python 调用保留 `task_id` 单入口。
- 输出继续使用 `schemes.jsonl` 和 `ga_summary.json`。

### 第二阶段：候选池模块落地

- 新建 `ml/scheduling_v2`。
- 实现数据加载、模板生成、教室排序、时间覆盖采样。
- Candidate Pool Builder 产出 task-level 完整候选。
- 增加单元测试验证每个候选课时数完整、`time_slot_id` 来自 DB 映射。

### 第三阶段：GA Solver 重构

- 实现 `gene = candidate_index` 编码。
- 初始化种群使用 GRASP、多策略贪心和随机混合。
- fitness 使用 O(n) 哈希检测硬约束。
- 输出满足 `scheme_count` 的多样化 TopK 方案。

### 第四阶段：替换旧入口

- `ml/api/routers/ga.py` 调用 `scheduling_v2.pipeline`。
- 移除或关闭 V2 Beam Search 直出方案逻辑。
- Java 入库流程保持不变，但保留二次冲突检测。

### 第五阶段：反馈闭环增强

- 人工调课记录进入训练样本。
- Room Ranker 使用确认、拒绝、调整行为迭代训练。
- 教师画像和影响因子权重进入可解释评分摘要。

## 验收标准

| 检查项 | 标准 |
|--------|------|
| 输入接口 | Python 仅依赖 `allocation_task_id` 加载上下文 |
| 候选完整性 | 每个 task candidate 展开后的课时数等于教学任务课时数 |
| 时间片合法性 | 所有 `time_slot_id` 均来自 DB，不使用公式推导 |
| 硬约束检测 | 教师、班级、教室冲突可 O(n) 检出 |
| 多方案输出 | 输出方案数符合 `scheme_count`，或返回明确失败原因 |
| 教师画像影响 | 硬不可排参与候选过滤，软偏好进入 fitness |
| 影响因子影响 | 生成配置权重能改变方案排序或搜索结果 |
| 可解释性 | `ga_summary.json` 包含候选池、fitness、冲突和参数摘要 |

## 答辩口径

如果被问“模型和 GA 谁起主要作用”，可以回答：

> 模型不直接生成课表，也不负责判断硬约束。模型学习历史排课和人工调课偏好，
> 用来生成并预评分每个教学任务的高质量候选集。GA 则在这些候选集之间进行
> 全校范围的组合搜索，通过硬约束检测保证合法性，并通过教师画像和影响因子
> 优化方案质量。

如果被问“为什么不直接用 Beam Search”，可以回答：

> Beam Search 更适合逐步构造局部解，但高校排课存在大量跨班级、跨教师、跨教室的
> 全局冲突。将完整教学任务候选作为 gene 后，GA 可以在压缩后的候选空间中做全局组合，
> 同时保留多方案、多样性和可行性优先选择，更适合 4000+ 教学任务规模。

如果被问“创新点是什么”，可以回答：

> 创新点在于把学习模型从“最终评分器”前移为“候选空间压缩器”，再用遗传算法做
> 全局无冲突组合优化。这样既利用了模型对历史偏好的学习能力，又避免让模型承担
> 硬约束排课的风险。

# 排课真实数据验收反馈

> 更新时间：2026-05-25
> 范围：记录真实任务端到端验收中发现的非阻塞问题，后续集中优化。

## 反馈 1：测试数据中机房容量不足导致任务不可行

### 现象

真实任务端到端生成时，ML API 返回失败：

```text
ValueError: 排课失败：教学任务缺少可行候选资源或模板集：21
```

定位到 `teaching_task_id=21`：

```text
课程：嵌入式系统
总课时：48
合班人数：74
要求教室类型：机房实验室
```

当前测试库中可用机房实验室最大容量为 60，因此 GA 在候选教室过滤阶段找不到满足：

```text
capacity >= 74
classroom_type == 机房实验室
```

的教室，任务被判定为不可行。

### 判断

该问题属于测试数据容量配置不够贴近现实场景，不是当前业务逻辑缺陷。

现实排课场景中，机房容量一般会覆盖对应教学班规模；暂时不为了该测试数据修改核心排课逻辑。

### 后续可选优化

- 补充更真实的测试教室数据，例如增加容量 80 以上的机房实验室。
- 在生成失败时，将不可行原因细分为课时、教室、时间片、教师硬不可排、模板枚举等具体类别。
- 后续如需要支持超容量合班，可再设计自动拆班或多教室协同排课逻辑。

### 当前处理

暂不修改业务逻辑，作为后续数据与诊断体验优化项记录。

## 反馈 2：候选方案 ID 使用全局自增，不按生成任务重置

### 现象

一次生成 3 个候选方案时，页面显示的方案 ID 可能是 `4、5、6`，而不是 `1、2、3`。

### 判断

这是因为 `allocation_scheme.id` 是数据库全局自增主键，不是“当前生成任务内序号”。不同排课任务、不同生成批次都会共享这个全局 ID 序列。

当前候选方案名称仍会按任务维度生成，例如：

```text
自训练模型方案 001
自训练模型方案 002
自训练模型方案 003
```

### 后续可选优化

- 前端候选方案列表弱化数据库 ID，优先展示“方案序号 / 方案名称 / 生成批次”。
- 如需更清晰追踪，可增加 `generation_batch_id` 或 `scheme_index` 字段。
- 保留数据库全局 ID 作为技术定位字段，不作为业务序号解释给用户。

### 当前处理

暂不修改表结构，记录为后续展示体验优化项。

# 拟采用的研究方法或技术方案

## 一、研究方法

### 1. 业务分析与数据治理

依据任务书和实际教学课表，梳理基础数据、教学任务、自动排课、人工调整及审核发布流程。分析非标准表格、名称不一致、周次差异和课时偏差，建立字段标准化、数据预检、冲突确认及批次追踪机制。

### 2. 约束建模

以教学任务及其授课单元为对象，采用绝对周次、星期和原子小节描述时间，关联全部教师、班级及教室资源。对重叠有效周次中的完整授课区间检查互斥，并建立容量、房型、禁排、有效周次和连排合法性约束。

将硬约束作为候选合法性条件，将任务覆盖和课时守恒独立审计。在合法方案上，以课程分散、教师紧凑、班级日负荷和教室偏好等惩罚构建加权评分：

$$
J(x)=\sum_{i=1}^{m}w_iS_i(x)
$$

其中，$S_i(x)$为定义并归一化后的软约束惩罚，$w_i$为可配置的非负权重。软评分不得用于抵消硬约束违规。

### 3. 启发式算法与多次求解

采用“任务Pattern构建—资源必要容量预检—任务优先级排序—合法候选枚举—贪心放置—有界局部重排—最终审计”的求解流程。必要容量预检用于发现明确资源缺口，通过预检不代表已经证明实例可排。

按绝对周次占用和释放资源，求解后按周安排签名派生动态模板。研究软约束评分对合法候选排序的影响，通过不同任务顺序或候选选择策略开展多次求解。保存配置、策略及随机种子（如使用），使结果可复现、可比较。

### 4. 实验与对比验证

使用合成数据覆盖边界与资源压力场景，使用实际教学数据完成任务书要求的验证。性能实验围绕100门课程、50间教室，明确任务和课次数量、约束配置、测试环境与计时边界，并重复运行报告耗时分布及排课质量。

通过冲突注入测试计算检出率，使用合法样本统计误报；分别比较基础规则、局部重排及不同软约束权重配置下的任务覆盖率、课时偏差、软约束惩罚和运行时间，不预先假定优化效果。

## 二、技术方案与系统架构

系统采用前后端分离与跨语言服务协同架构。

### 1. 前端交互层

采用React 19、TypeScript、Tailwind CSS与DaisyUI实现管理端。提供基础数据管理、导入预览、权重配置、排课作业进度、方案比较及周历课表。支持教师、班级、教室和周次等筛选，以及表单方式的精确周次微调；拖拽及冲突高亮作为交互增强。

### 2. Java业务层

采用Java 21、Spring Boot 4与MyBatis负责基础实体CRUD、访问控制、业务校验、人工复核、方案确认、正式课表查询及导出。使用RestClient提交Python作业并查询状态，正式计算不依赖Java请求线程持续等待。

身份认证和接口授权作为需完善的业务能力，与当前基础登录功能区分；具体认证组件以实际实施方案为准。

### 3. Python计算与数据处理层

采用Python（项目配置要求≥3.13）、FastAPI和Pydantic提供正式排课接口与请求校验。后台作业执行启发式求解及最终审计，通过占用索引、周次位掩码和候选缓存减少重复检查。性能优化依据测量结果开展，不预设全部计算由NumPy向量化实现。

利用Pandas等工具解析Excel与CSV，完成字段清洗、结构重建和异常反馈。导入与排课作为职责不同的模块，分别明确输入、输出及服务边界。

### 4. 数据持久化与一致性

采用MySQL存储基础数据、任务关系、生成作业、动态模板、精确片段周次、候选方案、正式安排及审核记录。利用活动任务唯一约束避免同一排课任务重复运行，以事务和发布锁保证方案确认的一致性。

本方案不将Redis作为必需组件；如后续存在明确缓存或并发需求，再依据实验和部署规模评估引入。

## 三、关键业务流程

基础数据导入与审核 → 教学任务及配置建立 → Java提交Python后台作业 → 状态持久化与前端轮询 → 候选草案及审计结果落库 → 精确周次人工微调与重审计 → 复核确认 → 事务生成正式课表 → 多角色查询、导出与打印。

方案修改与确认均由服务端重新校验；前端预校验只用于交互提示，不能替代提交时的约束检查。

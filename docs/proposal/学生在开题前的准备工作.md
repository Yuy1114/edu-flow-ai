# 学生在开题前的准备工作

自接受毕业综合训练任务书以来，本人围绕高校智能排课系统的课题目标，开展了业务资料整理、需求分析、约束建模、技术选型和原型开发等准备工作。目前已初步形成基于 Spring Boot、React 与 Python 的前后端分离及跨语言协同方案，并建立了启发式排课、冲突检测和人工复核的基础实现。对于约束权重调整、多次求解以及实际教学数据下的性能指标，已明确后续研究与验证方向。具体准备情况如下。

## 一、相关理论学习与算法路线分析

### 1. 排课问题与约束建模

高校排课涉及教师、班级、课程、教室及授课时间等多类资源，是具有复杂约束的组合优化问题。前期围绕排课问题的建模方法，重点学习了硬约束、软约束、资源占用和连续授课等基本概念。

硬约束用于确定排课方案的合法性，包括教师、班级和教室时间互斥，教室容量与类型匹配，以及授课周次和连排要求等。软约束用于评价合法方案的质量，包括课程周内分散程度、教师授课紧凑程度、班级日课时负荷及教室使用偏好等。

在此基础上，初步确定采用“优先满足硬约束，再评价软约束”的处理方式。同时将教学任务覆盖情况与课时完成情况纳入独立审计，避免出现课表无冲突但任务未排完整的问题。

### 2. 求解方法比较与技术路线选择

前期对遗传算法、整数规划和启发式规则等方法的基本原理及工程适用性进行了学习与比较。不同方法在求解质量、计算开销、约束表达及结果解释方面各有特点，具体性能需要结合数据规模和约束密度进行实验验证。

根据任务书允许采用“遗传算法或启发式规则”的要求，结合项目对合班教学、多周安排、连续授课及人工调整的处理需求，初步选择约束驱动的启发式规则作为自动排课的基础路线。通过资源预检、任务优先级排序、合法候选枚举、贪心放置和有界局部重排，构建可解释的排课过程。

后续将在合法候选选择过程中引入可配置的软约束评分，并通过不同任务排序或候选选择策略开展多次求解与方案比较。

## 二、实际教学资料整理与业务需求分析

### 1. 实际课表资料整理

已收集并整理学校实际班级课表文件，开展课表解析、字段标准化和数据一致性检查。重点关注课程、教师、班级、教室、授课周次、起始节次及连续课时等信息，为教学任务重建和实际数据实验准备基础材料。

初步分析发现，实际课表不能简单表示为每周重复的一张固定表。不同课程存在有效周次差异，部分教学活动涉及合班、连续实验课以及晚间或周末授课，声明课时与课表实测课时也可能存在差异。因此，系统需要保留精确周次和实际占用跨度，并对不一致数据提供人工审核机制。

### 2. 排课约束梳理

已初步梳理以下硬约束：

1. 同一教师在相同授课周次和重叠时间内不得承担多个教学活动，含协作教师的任务应检查全部教师。
2. 同一班级在相同授课周次和重叠时间内不得安排多门课程，合班任务应检查全部关联班级。
3. 同一教室在相同授课周次和重叠时间内不得被重复占用。
4. 教学任务学生总人数不得超过教室容量，教室类型应满足课程要求。
5. 连续授课应完整占用相邻小节，不得跨越规定的休息时段或拆分至不同日期。
6. 排课应满足教师禁排、资源启用状态、任务有效周次及固定或候选教室范围等条件。
7. 教学任务要求课时与实际安排课时应进行核对，未排任务和课时偏差不得被静默忽略。

软约束拟从课程周内分散程度、教师授课紧凑程度、班级日课时负荷和教室使用偏好等方面建立评价指标，并明确各项惩罚的计算方式及权重范围。

### 3. 功能与验收目标确认

依据任务书，系统需实现基础数据管理、批量导入导出、自动排课、约束权重调整、多次求解、手动微调、课表发布、导出打印及冲突自动检测。

性能与正确性验证将重点围绕两项要求开展：在定义的硬约束测试范围内达到冲突检出率100%；使用实际教学数据，在100门课程、50间教室的典型规模下，验证排课计算时间不超过30秒。

上述指标作为后续验收目标，需通过明确的数据集、测试环境和实验记录进行证明。

## 三、开发技术储备与工程环境准备

### 1. Java 业务服务

项目采用 Java 21、Spring Boot 4 与 MyBatis 构建业务服务，已开展教师、教室、班级、课程和教学任务等基础实体的管理接口及持久化实现。

Java 业务层负责排课任务提交、课表查询、人工调整、审核发布和导出等业务流转，并通过 HTTP 与 Python 排课服务协同。正式排课采用后台作业方式执行，前端通过定时轮询查询状态，避免长时间计算阻塞页面操作。

目前登录与角色信息处理具备基础实现，完整的身份认证、接口授权和操作人身份审计仍需进一步完善。

### 2. Python 排课与数据处理

项目采用 Python、FastAPI 和 Pydantic 构建算法服务及跨语言请求契约，并使用 Pandas 等工具开展课表文件解析、数据清洗和结构化转换。

排课原型以绝对周次和原子小节为时间坐标，检查教学活动的完整资源占用区间。通过占用索引、周次位掩码和候选缓存减少重复检查，并保留未排任务身份、缺失课时及失败原因，为人工处理提供依据。

### 3. React 前端

项目采用 React 19、TypeScript、Tailwind CSS 与 DaisyUI 构建管理端，已开展基础数据管理、课表网格展示、组合筛选和草案编辑等功能。

课表支持按教师、班级、教室及周次等条件查询。人工微调采用表单方式指定教室、星期、起始节次、连续节数和精确周次，修改后重新执行约束与课时审计。拖拽操作及落点冲突提示作为后续交互增强方向。

### 4. 数据库与部署环境

已建立基于 MySQL 的业务数据结构和前向迁移机制，涵盖基础实体、教学任务关系、排课作业、动态模板、正式课表及审核记录。

排课作业状态持久化保存，并通过数据库唯一约束防止同一排课任务重复进入活动状态。方案确认采用事务和发布锁机制，保证状态更新与正式课表写入的一致性。

已准备前端、Java 服务、Python 服务和数据库的开发运行环境，并建立容器化部署配置，为后续联调及实验复现提供基础。

## 四、算法原型与业务闭环准备

### 1. 启发式排课原型

已构建以教学任务为基本单位的排课原型。首先将总课时、每周次数、持续周数和连续节数转换为任务 Pattern，再进行资源必要容量预检及任务优先级排序。

求解过程中枚举满足硬约束的候选位置，采用贪心策略放置教学活动；初次放置失败时执行有界局部重排。任务完成后释放后续周次资源，最终按周课表签名生成动态周模板。

无法完成的任务保留具体原因和课时差异，进入人工复核流程。

### 2. 冲突检测与课时审计

已建立教师、班级和教室占用检查，以及容量、房型、连续节次和有效周次等校验逻辑，并开展相关约束、时间契约及动态周排课测试。

冲突检测在自动排课结果审计、草案修改和方案确认等环节执行。硬约束问题不得通过人工接受机制豁免；未排任务、Pattern 警告和课时偏差应显式展示并记录处理决定。

### 3. 人工复核与发布

已建立候选草案按精确周次新增、调整和删除的基础流程，每次修改后重新审计。通过审核的方案在事务中物化为正式课表，正式安排保存实际连续占用跨度，并纳入课时总账。

已具备多角色 Excel 课表导出基础，后续将继续完善打印及相关验收。

## 五、后续实验与完善计划

### 1. 实际数据性能实验

使用实际教学数据构建100门课程、50间教室的典型规模算例，明确教学任务数、教师数、班级数、授课周次、课次数量及约束配置。

实验将记录测试硬件、软件环境和计时边界，分别观察求解耗时与完整业务链路耗时，同时报告任务覆盖率、未排课时、硬冲突数和课时偏差，验证计算效率与结果完整性。

### 2. 冲突检出率实验

构造并标注教师、班级、教室时间冲突、容量不足、房型错配和非法连排等样本，通过冲突注入方式统计检出数与漏检数，同时使用合法样本检查误报情况。

以此验证任务书要求的100%冲突检出率，并区分“生成课表无冲突”与“检测器能够检出已知冲突”两项指标。

### 3. 权重调整与多次求解

完善软约束评分及权重配置，使权重变化能够影响合法候选选择。通过不同排序和候选选择策略开展多次求解，比较各方案的排课完成情况、软约束得分及计算耗时。

### 4. 功能验收与文献整理

继续完善基础数据批量导入导出、打印、权限控制和交互反馈，建立需求与验收用例的对应关系。

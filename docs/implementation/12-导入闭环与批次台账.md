# 导入闭环与批次台账

> 更新时间：2026-09-06
> 范围：真实课表 Excel → 解析 → 差异分析 → 人工复核决定 → 落库，以及这一过程留下的批次台账。
> 口径以根目录 `CONTEXT.md` 与 `docs/adr/0001` 为准。

## 链路

```bash
python -m ingest.parse_schedule_excel   --input <班级课表.xls> --output-dir <dir> --task-batch <批次>
python -m ingest.analyze_schedule_import --input-dir <dir>     # 与库内现状比对，产出冲突/新增/已匹配
python -m ingest.prepare_import_review   --input-dir <dir>     # 生成待决定的复核 CSV（只读）
#   人工在 import_review_items.csv 的 decision / merged_value 两列上做决定
python -m ingest.apply_import_review     --input-dir <dir> [--execute]
```

不加 `--execute` 是预演：读库、算出计划、回滚，不写任何一行，也不记台账。

## 真实课表的形状

一个班一个 `.xls`，单 sheet `推荐课表`，是「教学周 × (星期 × 大节)」的网格：

- 列头分两层：第一层是星期一～星期日，第二层是大节 `12` `34` `56` `78` `91011`。
- 行是教学周（第 1–20 行对应第 1–20 周），单元格形如 `L250\r\n91504`（教室 + 课程代码）。
- 表尾一行是课程说明连排：`Linux操作系统(L250)(ID[200250]学分[3.0]) 时[16] 师[段芃芃] 室[08202]【专】48人   游戏策划与运营(游248)…`
- 最后一行是作息说明，`晚上9-11节：19：10-21：35` 就是 11 节时间轴的来源。

## 三条容易丢掉的事实

**大节不是一节。** `12/34/56/78` 各占 2 个原子小节，`91011` 占 3 个。occurrence 记录
`period_index`（大节起始）与 `consecutive_slots`（占用小节数）两列，缺后者会让下游把
一次 2 节的课算成 1 节。

**网格已经说明了教学节奏。** 每周几次、连续几周、一次几节、哪些周有效，都能从网格直接
数出来，不需要按课时查表推断。`_derive_pattern` 输出 `sessions_per_week`、`duration_weeks`、
`session_slots`、`observed_hours`、`active_weeks`、`pattern_regular`。

**课程说明是连排的。** `【专】48人` 是上一门课的班型与人数标注，会粘在下一门课名前面，
`_clean_course_name` 负责剥掉。

## 节奏只在自洽时才写库

`teaching_task` 的入口校验要求 `每周次数 × 持续周数 × 每次课时 == 总课时`。真实数据经常
不满足，此时不能猜——写入一个不自洽的 pattern 会让课时审计从第一天就是错的。
`_importable_pattern` 的四条判定：

| 情况 | 处理 |
|---|---|
| 自洽 | 写入 `sessions_per_week` / `duration_weeks` |
| 各周次数不一致 | 留空，notes 记「课表节奏不规则(…)，待人工确认」 |
| 声明课时 ≠ 课表实测课时 | 留空，notes 记两个数字 |
| 乘不出总课时 | 留空，notes 记「不自洽」 |

留空表示交回引擎按课时推导，同时把实测值写进 notes 供人工判断。

## 冲突确认策略

`import_review_items.csv` 每行一个待决定项，`allowed_decisions` 给出可选项：

| decision | 含义 |
|---|---|
| `keep_db` | 保留库内旧值 |
| `use_import` | 采用导入值 |
| `merge` | 人工给出第三个值，写在 `merged_value` 列 |
| `ignore` | 本次不处理 |
| `create` / `create_after_dependencies` | 新增实体（新增项专用） |

`merge` 没有填 `merged_value` 会被显式拒绝并计入异常，不会悄悄退回导入值。

## 五类结果

一次执行的结果分成五类，同时写进报告和台账：

| 类别 | 含义 |
|---|---|
| 新增 created | 新建了课程/教师/教室/班级/教学任务 |
| 更新 updated | 字段被 `use_import` 或 `merge` 改写 |
| 冲突 conflicts | 复核项中两边不一致的字段数 |
| 异常 anomalies | 系统没能应用：依赖没解析出来、字段不支持自动落库、merge 没填值 |
| 跳过 skipped | 人工明确说不动（`ignore` / `keep_db`） |

异常与跳过必须分开：跳过是人的决定，异常是系统没做到，混成一类异常就看不见了。

## 批次台账

`import_batch`（迁移 015）为每次 `--execute` 记一行：来源目录、来源类型、`task_batch`、
执行人、状态、五类计数和完整摘要 JSON。通过 `task_batch` 可以反查这批导入产生的教学任务。

台账写入失败不会回滚已经提交的导入——数据已经在库里，丢一行来源记录，比谎报导入失败要好。

## 不可训练标记

课表记录能不能直接当训练样本，是任务级判定，`trainable` 与 `untrainable_reason` 两列随
`teaching_tasks.csv` 输出，并按课程代码带到每一条训练样本上。判为不可训练的四种情况：

- 课程本身不需要常规排课（毕业实习、毕业设计，虚拟教师、虚拟教室）
- 课表里没有可用的授课记录
- 声明课时与课表实测课时不一致
- 各周授课次数不一致

**只标记，不丢弃。** 样本照常导出，由训练阶段决定用不用。静默把可疑记录混进训练集，
会让模型学到一个学校从没执行过的课表。

## 真实数据实测（2026-09-06）

40 个真实班级课表文件、212 条教学任务：

| 指标 | 结果 |
|---|---|
| 拿到实测节奏的任务 | 212 / 212（此前为 0） |
| 声明课时 = 课表实测 | 120（57%） |
| 课表实测更多 / 更少 | 70 / 22 |
| 各周次数一致（规则） | 41 |
| 可自动写入节奏 | 29；其余 183 留空并注明原因 |
| 课程名仍带标注前缀 | 0（修复前普遍存在） |

单文件端到端（对真实 MySQL）：解析 6 门课 132 条占用 → 24 个实体新增 → 台账 1 行
`APPLIED / created=24`；其中 1 条任务写入了 `4次/周 × 5周` 的节奏，5 条留空并写明原因。

冲突与合并（人为把教室 08202 容量改成 999，导入值为 120）：

- `merge` + `merged_value=88` → 最终容量 88，台账 `updated=1, conflicts=1`
- `merge` 不填值 → 容量保持 999，台账 `anomalies=1`，报告写明 `merge decision without merged_value`
- 预演（不加 `--execute`）→ `import_batch` 零行，库内无改动

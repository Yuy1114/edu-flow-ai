# 第一阶段正式排课链路验收

> 范围：使用模拟或人工构造的基础数据，通过真实 MySQL、Python 作业服务、Java API 和管理端，证明“教学任务 → 动态模板草案 → 人工复核 → 正式课表”的 rules-only 闭环。真实历史数据清洗与模型训练属于第二阶段。

## 权威链路

```text
allocation_task + teaching_task 关系
  → POST /api/allocation-tasks/{id}/templates/generate
  → Python 持久作业 schedule_generation_run
  → pattern 构建与绝对周排布
  → 动态模板、精确 fragment week 和候选 scheme 同事务入库
  → 模板草案按周查询/新增/移动/删除
  → 每次修改重新执行硬约束与课时审计
  → 必要时显式接受不可豁免项之外的人工复核项
  → POST /api/allocation-schemes/{id}/confirm
  → 1/2/4 节授课单元物化为 course_assignment
  → 教师/班级/课程/教室/周次/星期组合查询与正式课时终审
```

正式入口固定 `trainModel=false`、`importDb=true`、`truncateDb=false`。LightGBM 不参与第一阶段的 pattern、可行域或候选顺序。

## 时间与教学任务契约

- 每天 10 个 45 分钟原子小节：上午 1–4、下午 5–8、晚上 9–10。
- 自动排课默认只使用周一至周五 1–8；人工草案编辑可显式使用晚间和周末。
- 理论/实践通常连续 2 节，上机/实验通常连续 4 节；人工尾差允许单独补 1 节。
- 一个教学任务直接关联一名主讲、可选协作教师和一个或多个班级。合班不拆成平行单班任务。
- 教室必须同时满足启用状态、容量、房型以及固定/候选教室范围。
- 教师硬禁排、任务 `allowed_weeks`、全部教师和全部班级关系必须穿透到最终片段。

## 发布状态机

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| `CREATED` | 输入可编辑 | 修改任务/配置，发起生成 |
| `RUNNING` | Python 作业已持久预留 | 只查询状态，不允许编辑/确认 |
| `GENERATED` | 完整候选已落库 | 编辑草案、重审计、确认 |
| `NEEDS_MANUAL_REVIEW` | 候选可查看，但有未排、pattern 警告或课时差 | 补排/删除/移动，或填写原因接受非硬问题 |
| `BLOCKED` | 输入、资源身份、硬冲突或落库校验失败 | 展示具体原因，修复输入后重试 |
| `FAILED` | 作业进程、配置或基础设施失败 | 展示错误，修复后重试 |
| `CONFIRMED` | 正式课表已物化 | 查询或通过正式课表接口人工微调 |

有候选方案或已确认的排课任务不能通过旧版 scheme/item API 重开、改绑或绕过审计；需要重新生成时新建排课任务。`time_slot` 是迁移维护的只读标准目录。

## 草案人工闭环

- 草案 API 使用真实 `template_fragment_id`，不使用负数虚拟 `allocation_item` ID。
- 人工片段必须显式选择动态模板、教学任务、教室、星期、起始节次、连续节数和一个或多个精确周次。
- 所选周必须属于该模板的 `week_numbers`；可以选择任意单周或非连续周。
- 每次新增、移动或删除都持有 scheme 行锁，刷新片段教师/班级/slot/week 关系并重新审计。
- 教师/班级/教室冲突、容量/房型、非法时间块、无效资源、禁排和关系漂移属于硬问题，永远不能人工豁免。
- 未排任务、pattern 警告和课时偏差可以填写原因显式接受；接受记录包含生成批次、复核项指纹、原因、复核项和时间。草案变化后旧接受自动失效。
- 当前第一阶段未接真实权限认证，操作人明确记录为本地演示操作员，不冒充已认证教务身份。

## 确认与正式课表不变量

- 确认事务获取全局 publication lock、scheme 行锁和 allocation task 行锁。
- 只允许 `CANDIDATE` 且任务处于 `GENERATED` 或已完成复核的状态进入确认。
- 确认前重新读取当前关系、重新审计，并对数据库中全部 ACTIVE 正式安排逐条检查教师、班级和教室的完整原子占用区间。
- 方案状态、任务状态和正式 assignment 在一个事务中更新；任何一条失败全部回滚。
- 正式课表使用 `consecutive_slots` 保存 1/2/4 节实际占用，查询网格展开每个原子小节。
- 正式课表人工新增、移动、更新和停用与确认共用全局锁；状态、来源方案和教学任务身份不能由普通更新偷换。
- 每次正式调整返回该任务课时审计；正式课表页面持续显示逐任务和全局应排、已排、少排与超排。
- 被 ACTIVE 正式课表引用的教学任务、课程、教师及画像、班级、教室暂时采用 fail-closed 冻结，避免查询时被原地改写。需要修改时先显式停用相关正式安排。

## 数据库与作业门槛

- `backend/db/migrate.sh` 必须能在空库完整执行，并在同一库重放为全部 `already applied`。
- 旧库必须通过 forward migrations 补齐原子时间轴、显式 pattern、生成作业状态、64 位模型版本字段、全局发布锁和精确 fragment week。
- Python 作业状态保存在 `schedule_generation_run`，Java 重启或停止轮询不会丢失状态。
- 管理端重新打开页面后必须恢复上次选中的排课任务，重新读取持久作业状态；若为 `RUNNING`，继续轮询至作业终态。任务切换后，旧请求不得回写当前任务的模板、周映射或错误状态。
- 前端轮询窗口与作业最长执行时间统一为 30 分钟；`BLOCKED/FAILED` 的原因保持在页面上，不得只显示短暂 toast。
- 作业进程重启时，对遗留 `QUEUED/RUNNING` 先解析作业日志的 terminal sentinel；如日志未完整落盘，再检查是否已原子提交同批候选方案。有可验证终态或候选时恢复为 `SUCCESS/NEEDS_MANUAL_REVIEW/BLOCKED`，只有两者都不存在时才标记 `FAILED`，不得丢失已提交结果或永久停在运行中。
- 模板草案表和候选 scheme 使用同一个连接、同一个事务；缺表、批次不一致或 scheme 写入失败时所有模板行回滚。
- `BLOCKED/NEEDS_MANUAL_REVIEW` API 必须直接返回具体 hard blockers/manual reviews，不能只返回容器内文件路径。

## 真实端到端检查

至少使用一组理论课双班任务和一组包含助教/禁排/固定或候选教室的任务完成：

1. 空库迁移后确认 `time_slot=18×7×10=1260`。
2. 通过 Java 发起生成，轮询到 `SUCCESS` 或 `NEEDS_MANUAL_REVIEW`，数据库任务状态一致。
3. 查询草案，确认同一 `generation_run_id`、具体周次、全部教师/班级和连续 2/4 节。
4. 把片段改为一个精确周，确认其他周消失且课时审计变为少排；恢复周次后重新吻合。
5. 构造课时尾差并接受人工复核，确认硬问题仍不能接受，草案变化后旧接受失效。
6. 确认方案，检查正式 assignment 数量、`consecutive_slots`、课程/教师/助教/班级/教室过滤和课时总账。
7. 人工移动到晚间或周末合法 slot 后仍无硬冲突；删除最后一次课后该任务仍出现在 UNDER 审计中。
8. 验证运行期 time-slot 修改、旧版 scheme/item 旁路、已确认主数据修改和重复确认均被拒绝。
9. 在 1440px 与 390px 下检查模拟实验台、草案编辑页和正式课表查询页。

## 第二阶段准入

第一阶段通过只说明规则引擎和产品闭环可作为基线，不说明现有历史样本可直接训练。第二阶段按以下顺序开始：

1. 重建历史合班教学任务，统一稳定教师/班级/教室 ID、真实容量、房型、人数和 10 节时间轴。
2. 按学期划分 train/validation/test，禁止同一合班事件或近重复组合跨集合泄漏。
3. 只在硬可行候选中训练排序器；历史安排作为弱正反馈，人工确认/调整/拒绝提供强弱不同的标签。
4. 建立 rules-only 与 model-guided 同批任务消融，模型不得降低任务覆盖率、硬约束和课时守恒基线。

在数据审计门槛通过前可以开始数据清洗与标签规范设计，但不能使用旧 LightGBM/CatBoost 产物宣称训练完成或进入发布。

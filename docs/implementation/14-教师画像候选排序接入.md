# 教师画像候选排序接入

教师画像从 V3 的 CP-SAT objective 迁到动态模板引擎的作用点：**候选排序软偏好**。画像决定"先试哪个格子"，不决定"哪些格子存在"。决策记录见 `adr/0004-rank-candidates-with-teacher-profiles.md`。

## 链路

```
MySQL teacher_profile.profile_preference_json（教师声明）
        │
        ├─ 画像基线 data/profiles/v3/teacher_profiles_v3.json（历史统计派生）+ 反馈聚合证据
        ▼
Java TeacherProfileDocumentService.finalProfilesForAllocationTask(taskId)
        │  {教师ID: final_profile}   ← 只包含"确实带至少一条偏好"的教师
        ▼
POST /api/ml/pipeline/jobs  { ... , teacherProfiles }
        ▼
Python app/api/v1/pipeline.py → <job log>.teacher_profiles.json → scheduler.run_pipeline --teacher-profiles
        ▼
scheduler/run_pipeline.py → pipeline_runs/<run>/teacher_profiles.json（随作业落盘的证据）
        ▼
scheduler/phase_scheduler.py → build_phase_cover(teacher_preferences=…)
        ▼
scheduler/teacher_preferences.py → PreferenceRanker.order_for() → find_spot 按分排序试格子
```

## 排序口径

七个维度，每个 0~1，取已声明维度的加权平均（`WEIGHTS` 一处常量表）：

| 维度 | 取值 | 来源 |
| --- | --- | --- |
| `early_period` | 1 − 覆盖到第 1~2 节的比例 | 声明 `avoidFirstPeriod`／派生 |
| `late_period` | 1 − 覆盖到第 9~11 节的比例 | 声明 `avoidLastPeriod`／派生 |
| `preferred_weekday` | 命中偏好星期记 1，否则 0 | 声明 `preferredWeekdays` |
| `preferred_period` | 命中偏好节次记 1，否则 0 | 反馈聚合 `preferred_periods` |
| `daily_load` | 预测当次课后的当日课次是否超过上限 | 声明 `preferredMaxDailyHours` |
| `compactness` | 该片段有效周里"当天已有课"的周占比 | 声明 `preferCompactSchedule` |
| `room_type` | 教室池按偏好房型重排（不裁剪教室） | 画像 `preferred_room_types` |

多教师任务逐维度取最小值：一个格子只有对所有教师都合意才算好格子——与硬约束"任一教师被占即不可行"同向。同分时退回引擎自己的均衡倾向（任务已用天数升序）与天次序号，排序因此始终确定。

未声明的维度**不参与**加权（不会被记 1.0 稀释），所以"只提了一条要求的教师"在排序里仍然有话语权。

## 硬约束与课时守恒不动

- 可行性只看 `DynamicSemesterSchedule.base_free` / `room_free`：教师、班级、教室互斥、不可用矩阵、房型与容量、单日节数上限 `TEACHER_DAY_CAP = 6`。
- 排序给出的候选如果全都不可行，仍然回落到引擎原有的确定性循环；排序不会让一个原本能排下的任务变成排不下（`test_the_only_feasible_slot_is_used_even_when_the_profile_dislikes_it`）。
- 课时守恒照旧：`final_hour_audit` 是唯一判据，画像不做任何"少排一次课来满足偏好"的让步。

## 读数：cover-report 的 `profile_satisfaction`

生成侧事后评估，分量名与 Java 方案满意度一致（`early_period` / `late_period` / `preferred_weekday` / `preferred_period` / `daily_load` / `room_type`）：

```json
{
  "profile_applied": true,
  "teacher_count": 12, "avg_satisfaction_score": 0.93, "avg_preference_score": 0.86,
  "low_satisfaction_count": 2, "low_satisfaction_threshold": 0.7,
  "covered_teacher_count": 12, "covered_fragment_count": 46, "ranked_fragment_count": 46,
  "weights": { "early_period": 1.0, "…": 0.6 },
  "teachers": [{ "teacher_key": "id:12", "declared_dimensions": ["early_period"],
                 "satisfaction_score": 0.83, "preference_score": 0.0, "components": {}, "evidence": {} }]
}
```

两个分数口径必须分开读：

- `satisfaction_score`：六分量等权、未声明记 1.0，**与 Java `/v3/satisfaction` 对齐**，用来跟既有画像页的数字比对。
- `preference_score`：只对教师已声明的维度取平均，`low_satisfaction_*` 按它判定——否则"只提了一个要求"的教师会被 1.0 稀释成 0.83 而看不出问题。

## 实测：接入前后（真实 pattern，重建教室池，探针偏好）

数据源：`backend/data/pipeline/v3.5/runs/20260803_162331/`（真实历史 run，10,166 条 pattern、720 名教师、17 个动态模板）。教室池从该 run 的真实课表反推（`classroom_name` → `required_room_type`，容量统一给 200）——**容量比真实宽松，绝对数字不能与历史报告对齐**；但两次跑用同一个池，所以差值是可信的。偏好是按真实教师姓名合成的探针（每 3 位教师给 1 位：避早课 50%、避晚课、紧凑、偏好星期 1~3、日上限 4 课次），因为本机 MySQL 未起、读不到真实声明画像。

| 指标 | 接入前 | 接入后 |
| --- | --- | --- |
| 完成教学任务 | 8,986 | 8,986 |
| 未排任务 | 1,180 | 1,180 |
| 硬冲突（教师/班级/教室） | 0 / 0 / 0 | 0 / 0 / 0 |
| 课时守恒通过任务 | 8,630 | 8,630 |
| 校验问题数 | 2,716 | 2,716 |
| 排课量（片段×周） | 154,267 | 154,240 |
| 画像覆盖教师 / 被排序片段 | — | 240 / 6,486 |
| `avg_satisfaction_score` | 0.7876 | 0.8022 |
| `avg_preference_score` | 0.6328 | 0.6526 |
| `low_satisfaction_count`（阈值 0.7） | 158 | 149 |
| 耗时 | 78.5 s | 114.3 s |

读法：
- **可行域没被动过**：完成数、未排数、硬冲突、课时守恒、校验问题数逐项相同——这正是 ADR 0004 要守的东西，在 1 万条真实 pattern 上成立。
- **排布确实变了**：97.3% 的排课（片段×周）位置或教室发生变化。贪心一遍过 + 共享资源池，早期格子一改会级联到后面，这不奇怪；这也是"必须用满足度读数而不是"感觉没变"来判断接入效果"的原因。
- **收益不大也不假**：偏好满足度 +0.02、低满足教师 −9。探针偏好很激进（同时要求避早晚课 + 紧凑 + 限定星期 + 日上限 4），在一个已经很满的真实课表里能被满足的空间本来就小。
- **代价要记**：耗时 +45%（78.5 s → 114.3 s）。排序在每个候选上调 `day_load`/`day_sessions`，是有真实成本的功能，不是免费的正则化。

## 已知边界（本轮明确没做）

- **真机（真实教室表 + 真实声明画像）还没跑**：容器栈（MySQL/Java/Python）本轮未启动。
  已用真实 pattern + 从真实课表反推的教室池 + 合成探针偏好跑出内部可比的差值
  （见 `implementation/14`：完成数/冲突/课时守恒逐项相同，`avg_preference_score` 0.6328 → 0.6526，
  低满足 158 → 149，耗时 +45%）；起栈后应当用真实声明画像复跑一遍并把绝对量对齐历史报告。
- **Java 落库与前端展示未做**：`profile_satisfaction` 只进 cover-report 文件，方案详情页还没有
  "低满足教师 + 主因"的展示；按 roadmap §4 仍是未完成项。
- **权重不开放配置**：改口径只能改 `WEIGHTS` 常量（有意为之，见 ADR 0004）。
- **`preferred_room_types` 没有生产方**：引擎与报告都支持，但声明解析与反馈聚合都不产出它。
- **声明侧 `preferredMaxDailyHours` 是小时、引擎按课次比较**：沿用 Java 既有比较口径，未做换算。

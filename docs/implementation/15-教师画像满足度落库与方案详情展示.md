# 教师画像满足度落库与方案详情展示

`implementation/14` 让画像回到排课引擎并把读数写进 cover-report 文件；本轮把这份读数**落进库、按方案展示出来**——也就是 roadmap §4 最后一项（低满足教师与主因）。数据流：

```
build_phase_cover(teacher_preferences=…)
        │  report.profile_satisfaction          全学期口径（教师跨模板合并）
        │  report.profile_satisfaction_templates 逐模板口径（一份模板 = 一份候选方案）
        ▼
export_db_draft(profile_satisfaction_templates=…) → db_draft/schedule_teacher_satisfaction.jsonl
        ▼
validate_export  ← 草案校验（模板引用、分数区间、唯一键、条数>0）
        ▼
import_db_draft_to_mysql → MySQL schedule_teacher_satisfaction（迁移 017）
        ▼
AllocationTeacherSatisfactionMapper.findByRun(taskId, runId)
        ▼
AllocationTemplateDraftView.satisfaction → GET /api/allocation-schemes/{id}/template-draft
        ▼
方案详情页「教师画像满足度」卡片（低满足教师 + 主因，展开可看全部读数）
```

## 为什么按模板（方案）落库

一次生成产出 **17 个动态周模板**，各覆盖不同周次，各自是一份候选方案。把 17 份混在一起平均出来的分数不指向任何一个"方案"，方案详情页要的正是"**这一份方案里谁不满意、卡在哪一维**"。所以：

- 行粒度 = `(allocation_task_id, generation_run_id, template_code, teacher_key)`；
- 模板片段用 `template_week_mask`（该模板实际负责的周）而不是全学期 `week_mask` 计算，避免同一个片段在多个模板里被重复计入。

## 落库结构（`backend/db/017_schedule_teacher_satisfaction.sql`）

| 列 | 含义 |
| --- | --- |
| `template_code` | 对应 `schedule_template.template_code`，按编码挂钩而不是模板 ID（ID 是导入时生成的） |
| `teacher_key` | 引擎里的教师键：`id:<数字>` 或 `name:<姓名>`；**唯一键用它**（同名教师只能靠姓名区分，引擎本身也区分不了，不猜） |
| `teacher_id` | 画像键是 `id:` 时才有值，姓名键为 `NULL` |
| `item_count` / `days_used` | 该教师在这份模板里的排课量（片段×周）与占用星期数 |
| `satisfaction_score` | 六分量等权、未声明记 1.0，与 AI 侧旧口径可比 |
| `preference_score` | 只对教师已声明维度取平均 |
| `low_satisfaction` | **生成侧判定的结论**（`preference_score < 0.7`），展示端只读不重算 |
| `declared_dimensions_json` / `components_json` / `evidence_json` | 教师声明过哪些维度、六分量分项、命中/超限计数 |

`low_satisfaction` 存成列而不是让展示端自己比阈值，是因为"低满足"这个判断只能有一处：否则生成侧和页面各判一次，迟早对不上。阈值仍是两处常量（Python `teacher_preferences.LOW_SATISFACTION_THRESHOLD`、Java `MlTeacherProfileController.LOW_SATISFACTION_THRESHOLD`），两侧注释都写明改一处要改两处。

`schema.sql` 不随迁移同步（016 也不在里面），所以本轮只登记迁移到 `backend/db/migrate.sh`，没动 `schema.sql`。

## 展示端

- 后端：`AllocationTeacherSatisfactionView`（整体读数 + 低满足明细）挂在 `AllocationTemplateDraftView.satisfaction` 上，页面**一次请求**拿到排课表与满足度。
- 主因 = 该教师**已声明维度里得分最低的那一维**（Java 侧算 `primaryReasonDimension`，前端负责翻成人话：`偏好星期命中 0/5`、`10 天超过每日 4 次`）。数字全部取 `evidence`，页面不重算。
- 整体读数按教师聚合再平均（同一位教师在多个模板里各有读数，先按人平均，避免排课多的教师拉偏均值）。
- 前端 `TeacherSatisfactionPanel`：`profileApplied=false` 时**整段不渲染**（本次生成没有画像参与，它列不出任何东西，不需要提示）。
- 表不存在时（例如线上库还没跑 017）方案详情**不整页 500**：记一条 `log.warn` 后按空块返回。

### 顺带修掉的一处口径冲突

`MlTeacherProfileController` 原来用 `satisfaction_score < 0.7` 判低满足，生成侧用 `preference_score < 0.7`——同一个概念两处判据不同，同一位教师可能在画像页不算低、在方案页算低。已按生成侧统一为 `preference_score`（该接口补出 `preference_score` / `declared_dimensions` / `low_satisfaction` / `avg_preference_score` / `low_satisfaction_threshold` 字段）。Java 侧未接教室类型，`room_type` 恒为 1.0 且不进声明维度，`note` 里已写明。

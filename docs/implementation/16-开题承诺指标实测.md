# 16 - 开题承诺指标实测（排课耗时与冲突检出率）

开题材料里写下的两个验收目标在这之前**一次都没测过**（`proposal/学生在开题前的准备工作.md`、
`拟解决的主要问题和最终目标.md`）：

1. 100 门课程 / 50 间教室的典型规模下，排课计算时间 ≤ 30 秒；
2. 规定硬约束范围内的**冲突检出率 100%**。

开题材料同时还要求"说明教学任务数、教师及班级数量、授课周次、课次数量、约束配置、测试硬件及
计时边界，同时报告任务覆盖率、未排课时、硬冲突和课时偏差"，所以本文按这个清单逐项给出实测值，
而不是只写两个数字。所有数字都来自 `backend/python/scripts/` 下的两个脚本在真实语料上的运行，
产物在 `backend/data/analysis/promise_scale/`（数据目录不入版本管理）。

## 0. 结论摘要

| 指标 | 实测 | 结论 |
|---|---|---|
| 排课计算时间（开题口径：100 门课程 / 50 间教室） | **中位 10.63 s**（5 次：9.62 / 10.52 / 10.63 / 10.85 / 11.15） | ✅ 满足 ≤ 30 s |
| 排课计算时间（同批课程、教室补到 74 间的对照） | **中位 0.661 s**（0.650 / 0.654 / 0.661 / 0.665 / 0.682） | ✅ 满足 ≤ 30 s |
| 冲突检出率（11 类硬约束逐类注入） | **11 / 11 = 100%** | ✅ 满足 100% |
| 合法课表误报 | 冲突类（教师/班级/教室占用、房型、容量、时间轴）**全部 0** | ✅ 零误报 |
| 生成出的课表硬冲突 | 教师 / 班级 / 教室占用 **0 / 0 / 0** | ✅ 无冲突 |
| 任务覆盖率（50 间教室） | 899 / 1,031 = **87.2%**（课时覆盖 92.5%） | 见 §3：教室供给不足所致 |
| 任务覆盖率（74 间教室） | 1,008 / 1,031 = **97.8%**；扣除 23 个语料容量缺口任务后 **100%** | ✅ |
| 课时偏差（50 间教室） | −2,767 节（−7.5%） | 见 §5 |

## 1. 算例定义

数据源是清洗后的真实语料，构造是确定性的（固定学期 + 固定排序 + 固定规则），换机器只有耗时不同：

| 项 | 值 |
|---|---|
| 学期 | `2023-2024学年1学期总课表`（5 个学期里任务最多，1,888 个任务 / 604 门课程） |
| 课程数 | **100**（按教学任务数降序取开课面最广的课程，并列按课程名） |
| 教学任务数 | **1,031** |
| 教师数 | **348** |
| 班级数 | **406** |
| 教室数 | **50**（真实教室池 369 间里按课时需求比例抽：48 普通教室 + 2 机房；容量取语料回填值 120） |
| 授课周次 | 语义周 18 周；单任务持续周数 2–18 周（8 周 488 个、10 周 200 个、4 周 132 个…） |
| 课次 | 每任务每次课 2 节的 975 个、4 节（上机/实验）的 56 个；每周次数由课时规则表定 |
| 总课时 | **36,891** 节（45 分钟/节） |
| 约束配置 | 时间轴每天 11 节（上午 1-4、下午 5-8、晚上 9-11）；**自动域 = 工作日 1-5 × 节次 1-8**（晚间与周末为人工保留域，ADR 0001）；阶段周 8 + 10；教室按房型与容量匹配 |
| pattern 来源 | 每个任务只给总课时，节奏交给引擎自己的规则表：`hours_rule` 990 个、`hours_exact_factor` 30 个、`hours_block_approximation` 11 个（近似者的课时差由审计显式报告） |
| 测试硬件 | Apple M4（10 核）、24 GB 内存、macOS 27.0.1、Python 3.13.13、单进程单线程 |

教学任务来自 `backend/data/parsed/history_training_dataset_v2/_tasks/teaching_tasks.csv`（5 个学期
重建出的 8,833 个真实任务），教室来自 `backend/data/parsed/history_training_dataset/_combined/classrooms.csv`。

## 2. 计时边界

指标必须说清量的是哪一段，否则 30 秒没有意义。本实验分开报三段：

| 段 | 内容 | 实测 |
|---|---|---|
| **主指标：引擎纯计算** | `build_phase_cover`：pattern → 动态周模板（本进程内，不含数据库、不含作业调度与落库） | 10.63 s（50 间）/ 0.661 s（74 间） |
| 链路后段 | 草案导出 `export_db_draft` + 校验 `validate_db_export`（同一份 cover，12,836 片段） | 0.468 s + 0.198 s |
| 整条作业链路 | 隔离栈上按下生成 → 状态终态（Java → ml-api → Python 子进程 → 引擎 → 导出 → 校验 → MySQL 落库） | **2.116 s**（fixture 规模：1 任务 / 2 教师 / 1 模板，轮询粒度 1 s） |

整条链路在 1,031 任务规模**没有实测**：那要求先把 1,031 个语料教学任务连同教师、班级、教室种进
MySQL，语料侧目前没有这条入库路径（`import_data.py` 走的是原始 xls 解析链路）。把两段相加得到的
**≈ 12.8 s ≤ 30 s 是估算值**，不是实测值，本文按估算标注。fixture 规模的 2.1 s 说明链路的固定开销
（子进程启动、作业轮询、草案写入与落库）在秒级，不随任务数增长。

## 3. 为什么要跑"资源供给"这套对照

50 间教室的自动域容量是 18 周 × 5 天 × 8 节 × 50 = 36,000 节，而 100 门课的课时需求是 36,891 节
（普通教室负载 101.7%、机房 122.2%）。也就是说**这个算例本身就超载**，排不完是资源不足的必然结果，
不能记到算法头上。所以同一批课程再跑一套 `resource_supply`（按"需求 / 0.7 余量"补到 74 间教室，
负载降到 ~70%）用来隔离原因：

| 配置 | 教室 | 负载（普通/机房） | 完成 / 总任务 | 课时覆盖 | 耗时中位 |
|---|---|---|---|---|---|
| `promise`（开题口径） | 50 | 101.7% / 122.2% | 899 / 1,031 = 87.2% | 92.5% | 10.63 s |
| `resource_supply` | 74 | 69.7% / 61.1% | 1,008 / 1,031 = 97.8% | 97.9% | 0.661 s |

两套配置的两次运行都是"逐轮质量完全相同"（同一输入 → 同一课表），硬冲突都是 0。50 间教室里未排
的 132 个任务里，23 个是**语料的容量缺口**（学生数 > 120，而全部教室容量都是回填值 120），
其余 109 个是 `automatic_search_exhausted`——教室被占满后无可放格子。教室补到 74 间后只剩那 23 个
容量缺口任务排不上，即**在可用资源下 100% 排完**。

## 4. 冲突检出率：11 类逐类注入

只报"生成出的课表没有冲突"是不够的——那说明的是没排错，不是**认得出错**。所以另做注入实验：
对真实 cover 的片段做最小改动，逐类注入一个已知冲突，要求审计在对应类别上报出来。

为此把生成期"顺手拦下"的硬约束检查提炼成可复算的审计函数
（`phase_scheduler.audit_placement_constraints`：教师/班级/教室占用、房型、容量、时间轴合法性；
课时守恒复用 `final_hour_audit`），实验代码在 `scheduler/conflict_injection.py`，
驱动脚本 `scripts/audit_conflict_injection.py`。

| 注入的冲突 | 期望检出 | 实测 |
|---|---|---|
| 同一教师同一格两节课 | teacher ≥ 1 | ✅ 8 处 |
| 同一班级同一格两节课 | class ≥ 1 | ✅ 16 处 |
| 同一教室同一格被占两次 | room ≥ 1 | ✅ 8 处 |
| 教室房型与要求不符 | room_type_mismatch ≥ 1 | ✅ 1 处 |
| 班级人数超过教室容量 | capacity_mismatch ≥ 1 | ✅ 1 处 |
| 课时少排（去掉一周） | hour_mismatch +1 | ✅ 144 → 145 |
| 课时超排（补一周） | hour_mismatch +1 | ✅ 144 → 145 |
| 节次越过时间轴末端 | time_axis_violation ≥ 1 | ✅ 1 处 |
| 星期越界（第 8 天） | time_axis_violation ≥ 1 | ✅ 1 处 |
| 周次越界（学期之外） | time_axis_violation ≥ 1 | ✅ 1 处 |
| 排进晚间人工保留域 | outside_automatic_domain ≥ 1 | ✅ 1 处 |

**检出率 11 / 11 = 100%，跳过 0，误报 0。** 两条额外证据：

- **合法课表零误报**：同一份真实 cover 不注入时，教师/班级/教室占用、房型、容量、时间轴**全为 0**。
- **与生成侧口径一致**：审计算出的课时守恒差额 144 与生成报告里的 `conservation_mismatch` **逐位相同**
  （144 = 132 个未排任务 + 12 个 pattern 自身不自洽的任务：11 个规则表近似 + 1 个整除因子不匹配），
  说明这个独立检查器不是另起一套标准。
- 计数口径：占用冲突报的是"重复占用的坐标数"（同一教师同一格两节课按周次 × 连堂节数展开），
  不是片段数；注入时如实记录顺带触发的其它类别（例如超排那条顺带撞了 2 处教师 / 4 处班级占用），
  不挑报。

## 5. 课时偏差与覆盖率的关系

`promise` 配置课时差 −2,767 节（需求 36,891 / 排出 34,124），全部来自未排任务；`resource_supply`
配置 −783 节。课时守恒审计逐任务给出差额与原因，未排任务同时进 `unresolved` 台账
（`classroom_capacity_unavailable` / `automatic_search_exhausted`），可以逐条追到具体任务。
审计口径与第一阶段"课时总账"一致：`r:before` 已有的 144 / 35 条差异都在台账里，不是本实验新引入的。

## 6. 已知边界（明确没做）

- **整条作业链路在 1,031 任务规模未实测**（见 §2），只有 fixture 规模的 2.116 s 与两段相加的估算。
- **教室容量是语料回填值 120，不是真实座位数**：所以学生数 > 120 的 23 个任务在算例里必然排不上，
  真实座位数补齐后这些任务与覆盖率需要重测。
- **教师身份在算例里是姓名**（语料遗留口径，见 `implementation/13`）：教师占用按姓名判定，
  同名不同人无法区分；真实教师 ID 接入后结论可能变化。
- **只跑了 1 个学期**：算例取任务最多的学期（2023–2024 学年 1 学期），其它 4 个学期的规模与耗时未测。
- **只跑了本机单进程**：没有测多进程/多机并行、也没有测内存峰值。
- **50 间教室那套是超载算例**：覆盖率 87.2% 反映的是教室供给（101.7% 负载），不是算法上限；
  压力场景按开题分工仍由合成数据承担（`/admin/simulation` 12 场景）。

## 7. 复现

```bash
cd backend/python && export PATH="$PWD/.venv/bin:$PATH"

# 1) 30 秒指标（两套资源供给 + 链路后段计时），产物写 backend/data/analysis/promise_scale/
env -u PYTHONPATH python scripts/bench_scale_promise.py --courses 100 --rooms 50 --repeat 5 --chain

# 2) 冲突检出率（读上一步的真实 cover，逐类注入）
env -u PYTHONPATH python scripts/audit_conflict_injection.py

# 3) 单测（含注入实验的契约测试）
env -u PYTHONPATH python -m unittest discover -s tests -t .
```

产物：`scale_example.json`（算例定义与硬件）、`bench_report.json`（耗时分布与两套配置的完整指标）、
`conflict_injection_report.json`（逐类注入结果）、`phase_cover_promise_run*.json`（课表）、
`chain_draft/`（草案与校验报告）。

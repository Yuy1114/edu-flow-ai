# V3.5 — 模板化排课落库设计

> 状态：当前实现契约
>
> 更新时间：2026-08-24
>
> 目标：支撑 V3.5 绝对周次排课、动态周模板压缩、精确周生效和后续局部调整。

## 一句话定义

V3.5 不直接只保存最终展开课表，而是保存：

```text
模板
  ↓
每周使用哪个模板
  ↓
模板内有哪些片段
  ↓
片段实际占用哪些课段
```

模板周映射负责选择当周的模板，fragment-week 关系则负责说明每个片段的精确绝对生效周。两者共同组成可查询、可审计的周语义。

## 统一时间坐标

`period_index` 表示 45 分钟原子小节，每天完整时间轴为：

```text
上午：1-4
下午：5-8
晚上：9-10
```

自动排课默认只使用周一至周五的 1-8；9-10 与周末保留为人工可编辑时段。理论课授课单元连续占 2 小节，实验/上机课连续占 4 小节，且不跨越上午、下午和晚间边界。

## 核心表

### 1. `schedule_template`

记录一次排课任务生成出来的模板实体。

用途：

- 保存模板编码，如 `cover_v1_template_1`。
- 记录模板属于哪个 `allocation_task_id`。
- 记录算法版本、模板顺序、片段数、任务数。

对应算法输出：

```text
template_cover_v1.json.templates[]
```

### 2. `schedule_template_week`

记录某个排课任务中，每一周使用哪个模板。

用途：

- 查询第 N 周应该套用哪份模板。
- 与 `schedule_template_fragment_week` 共同限定当周实际展开的片段。
- 查询、审计和正式物化都必须同时校验 `allocation_task_id + generation_run_id + template_id + week_number`。

在引入精确 fragment-week 后，不允许单独修改这张表来“换周”，否则片段的生效周会与模板映射分裂。第一阶段不提供独立换周 API；未来如需整周互换，必须在同一事务内同步改写周映射与受影响 fragment-week，然后重做全部硬约束和课时审计。

### 3. `schedule_template_fragment`

记录模板中的一个教学片段。

一个 fragment 表示：

```text
某个教学任务
在某个模板里
占用某个教室
从某天某课段开始
连续占用 consecutive_slots 个课段
```

对应算法输出：

```text
template.fragments[]
```

### 4. `schedule_template_fragment_slot`

记录 fragment 实际占用的每一个课段。

例如上机课：

```text
fragment: 周二第 5 小节开始，consecutive_slots = 4
实际占用：
  周二第 5、6、7、8 小节
```

用途：

- 快速做模板内冲突检测。
- 查询某模板某时间段有哪些课。
- 避免每次查询时动态展开 `consecutive_slots`。

### 5. `schedule_template_fragment_week`

记录每个 fragment 精确在哪些绝对周生效。

- 自动生成片段通常覆盖所属动态模板的全部映射周。
- 人工补排可以只选第 10 周，或选择任意非连续周，不再用“模板前 N 周”近似。
- 所选周必须是该 fragment 所属模板的映射周；审计、查询和正式物化都以本表为权威。
- 旧批次没有精确周关系时，才兼容使用 `duration_weeks` 展开，并由迁移回填。

### 6. `schedule_timetable_entry`（可选）

最终周课表展开表。

MVP 阶段可以不急着使用，因为通过：

```text
schedule_template_week
+ schedule_template_fragment
+ schedule_template_fragment_slot
+ schedule_template_fragment_week
```

已经能动态查询任意周课表。

如果后续前端或 Java 查询压力较大，再把模板展开成 `schedule_timetable_entry` 缓存。

## 草案数据文件与原子入库

Python 正式作业先将 `template_cover_v1.json` 导出为同一生成批次的可审计 JSONL 中间产物：

```text
backend/models/v3.5/placement/db_draft/schedule_templates.jsonl
backend/models/v3.5/placement/db_draft/schedule_template_weeks.jsonl
backend/models/v3.5/placement/db_draft/schedule_template_fragments.jsonl
backend/models/v3.5/placement/db_draft/schedule_template_fragment_slots.jsonl
backend/models/v3.5/placement/db_draft/schedule_template_fragment_weeks.jsonl
```

这些文件字段与 SQL 表保持同一生成批次身份。正式链路先做文件级结构校验，再将全部
模板表和 `allocation_scheme` 候选元数据放在同一个 MySQL 事务内写入；缺表、批次混用、
方案写入失败或发布闸门阻塞时不得留下半批次。

## 动态周模板映射策略

模板不再预先固定为 T1/T2，也不轮换套用。排课正确性先在绝对周次上建立：

```text
任务 Pattern
  -> 授课片段的绝对有效周集合
  -> 按 week + day + period 检查冲突并占位
  -> 展开每周实际课表
  -> 对完全相同的周课表签名去重
  -> 生成 schedule_template 与 schedule_template_week
```

任务达到要求课时后不再进入后续周次，它释放的教师、班级、教室和时段可被短周期课程继续使用。模板数量由实际每周活跃任务集合决定，但不超过学期周数。

## 周映射一致性

对任意 fragment-week 行，同一 `allocation_task_id + generation_run_id + week_number`
必须存在 template-week 行，且其 `template_id` 必须与 fragment 所属模板一致。
人工新增或移动片段时只能选择该模板已映射的周；每次修改后都重做审计。
模板化的收益是压缩重复周结构并保留精确周语义，不是绕过 fragment-week 一致性校验。

## 当前边界

- 模板查询必须使用同一个 `generation_run_id`，避免混用不同批次的周映射和片段。
- 自动搜索未完成的教学任务必须显式进入待人工处理清单，不得丢弃或写成已证明不可行。
- 原始总课时与实际占位课时的偏差作为终审结果展示，必须由人工确认。
- V3.5 候选只能通过模板草案专用接口新增、移动和删除片段；每次写操作后重新执行
  教师、班级、教室、房型、容量、禁排、关系身份及逐任务课时审计。
- 只有无硬问题的草案可以发布。单节尾差、未排任务或 pattern 警告可以由本地演示操作员
  填写原因后显式接受；接受记录带当前复核项指纹，任何复核项变化都会使旧接受失效。
- 确认发布在全局互斥事务中再次审计，并按 1/2/4 个原子小节物化为正式
  `course_assignment`；正式查询和人工调整之后继续显示逐任务及全局课时总账。
- `time_slot` 是迁移生成的 18×7×10 只读坐标目录，运行期 API 不允许改写。
- `schedule_timetable_entry` 暂时是可选缓存表，不是 MVP 必需表。

# 毕设最终系统架构设计

> 本文档定义 Edu-Flow-AI 毕业设计最终形态。它不是单点算法说明，而是从学校真实数据进入系统，到智能排课、人工反馈、教师画像演进、多角色课表导出的完整业务闭环。

> 本文于 2026-09-06 按 V3.5 基线重写。此前版本以 Placement Model + CP-SAT 描述排课核心，
> 那条链路的代码已在 `af96f4b` 删除、设计文档已归档到 `docs/archive/`，不再作为现状陈述。
>
> 每节都区分**已落地**与**待建设**：已落地的给出实现文档与验收记录，待建设的明确写成
> 设计意图而不是现状。领域口径以根目录 `CONTEXT.md` 和 `docs/adr/0001~0003` 为准；
> 排课实现细节见 `docs/architecture/22-V3.5-模板化排课落库设计.md`。
>
> 时间坐标为每天 11 个 45 分钟原子小节：上午 1–4、下午 5–8、晚上 9–11。晚间是学校作息里
> 19:10–21:35 的三节大块。自动排课默认只用工作日 1–8，第 9–11 节与周末为人工保留时段。

## 1. 设计目标

Edu-Flow-AI 的最终目标不是“生成一张课表”，而是构建一个面向学校教务场景的智能排课平台：

```text
历史数据导入
  → 资源建模
  → 教师画像生成
  → 智能排课
  → 人工调整 / 反馈
  → 画像更新 + 模型训练
  → 多角色导出
```

系统完成标准可以拆成三大业务能力：

1. **导入**：能够从历史课表、基础数据、教务表格中解析出真实课表、班级、教师、教室、课程等资源，并支持多轮导入中的冲突对比与人工确认。
2. **排课**：能够将导入数据与系统内自行创建的教学任务合并，生成质量高、美观、无硬冲突的候选排课方案。
3. **多条件导出**：能够面向学生、教师、教务、教室管理者等不同角色，导出各自视角下清晰可用的课表。

核心创新点是 **教师画像驱动的反馈训练闭环**：系统从历史课表、正式课表、调课变动、教师手动填写、人工反馈中持续提取画像信号，并将其作为模型特征、软约束目标和训练样本的一部分，使后续排课逐步接近真实使用者偏好。

## 3. 模块一：数据导入与冲突治理

> **状态：已落地（2026-09-06）。** 实现说明、真实数据实测与批次台账见
> `docs/implementation/12-导入闭环与批次台账.md`。

### 3.1 目标

导入模块负责把学校已有的“非标准数据”转成系统可计算的数据资产。

输入来源包括：

- 历史真实课表
- 班级、专业、课程、教师、教室等基础资源表
- 已确认的正式课表
- 后续调课、停课、补课记录
- 教务手工维护的数据

输出结果包括：

- `semester`
- `class_group`
- `course`
- `teacher`
- `classroom`
- `teaching_task`
- `schedule_item`
- 历史排课样本
- 教师画像原始证据

### 3.2 多轮导入冲突处理

学校数据经常会被多次导入，且不同文件之间存在冲突。系统不应静默覆盖，而应提供对比治理机制：

```text
新导入数据
  → 字段标准化
  → 与现有资源匹配
  → 识别新增 / 更新 / 冲突 / 删除候选
  → 展示差异对比
  → 教务人工选择保留策略
  → 写入正式数据
```

典型冲突包括：

| 冲突类型 | 示例 | 处理方式 |
|---|---|---|
| 同名不同 ID | 两个文件中都有“张三”，但工号不同 | 提示人工合并或保留为不同教师 |
| 同 ID 不同属性 | 同一教室容量变化 | 展示旧值、新值，由人工在四种策略中选择 |
| 课程归属变化 | 课程所属专业或年级变化 | 生成变更记录，避免直接覆盖历史样本 |
| 历史课表异常 | 声明课时与课表实测课时不符 | 标记为不可训练并写明原因，等待人工确认 |

人工决定的四种策略（`import_review_items.csv` 的 `decision` 列）：

| decision | 含义 |
|---|---|
| `keep_db` | 保留库内旧值 |
| `use_import` | 采用导入值 |
| `merge` | 人工给出第三个值，写在 `merged_value` 列；不填值会被拒绝并计入异常 |
| `ignore` | 本次不处理 |

一次执行的结果分成**新增 / 更新 / 冲突 / 异常 / 跳过**五类。跳过是人明确说不动，
异常是系统没能应用（依赖未解析、字段不支持自动落库、merge 没填值），两者必须分开，
否则异常会被跳过盖住。每次落库在 `import_batch`（迁移 015）记一行：来源、执行人、
状态与五类计数；预演不写台账。

### 3.2.1 从课表网格反推教学节奏

真实课表是「教学周 × (星期 × 大节)」的网格，它直接说明了每门课每周上几次、连续几周、
一次占几节。导入把这些如实记下来（`sessions_per_week` / `duration_weeks` /
`session_slots` / `active_weeks` / `observed_hours`），不再只带一个 `total_hours`
让引擎按课时查表推断。

但**只在自洽时才写库**：`teaching_task` 的入口校验要求
`每周次数 × 持续周数 × 每次课时 == 总课时`。40 个真实文件、212 条教学任务里，
有 92 条声明课时与课表实测课时不符（70 条实测更多、22 条更少），只有 41 条各周次数一致。
不自洽时留空并把实测值写进 notes 交人工确认——写入一个不自洽的 pattern，
会让课时审计从第一天就是错的。

### 3.3 与教师画像的关系

导入模块不仅构建基础资源，也为教师画像提供第一批证据：

```text
历史课表
  → 教师常用星期 / 常用节次 / 常用教室类型 / 日课时分布
  → 历史推断画像
```

## 4. 模块二：智能排课

### 4.1 排课输入

排课任务由两类数据共同组成：

1. **导入数据**：从历史课表和基础数据中解析出来的学校资源与历史规律。
2. **系统创建数据**：教务在系统内维护的新学期教学任务、课程安排、教师安排、教室资源和约束条件。

统一进入排课任务后，形成：

```text
allocation_task
  ├─ teaching_tasks
  ├─ teachers
  ├─ classrooms
  ├─ class_groups
  ├─ constraints
  └─ teacher_profiles
```

### 4.2 排课核心链路

当前第一阶段使用 rules-only 架构：

```text
规则可行域先保证时间、教师、班级、教室、房型、容量和课时约束
贪心放置 + 有界局部重排在合法候选中完成排布
无法自动完成的任务显式进入人工复核，不伪装成成功
```

分工如下：

| 组件 | 职责 | 不负责 |
|---|---|---|
| Pattern Builder | 根据显式任务节奏或 2/4 节授课单元构造 pattern | 不安排具体教室与时间 |
| Phase Scheduler | 在绝对周可行域内放置片段并执行局部重排 | 不放宽硬约束 |
| Template/Audit | 派生动态模板，输出未排任务、冲突和课时总账 | 不隐藏未解决问题 |
| Java 后端 | 管理持久作业、草案审计、事务发布和正式课表 | 不承担核心排布 |
| 前端 | 创建任务、恢复作业状态、查看/修改草案和查询正式课表 | 不绕过后端审计直接发布 |

第二阶段的 LightGBM 如启用，只能在上述硬可行候选中做排序增强，不能决定可行性或降低 rules-only 基线。

### 4.3 方案质量目标

最终候选方案需要同时满足：

- **硬约束无冲突**：教师、班级、教室、时间不可冲突。
- **资源合理**：教室容量、教室类型、校区等满足任务需求。
- **结构美观**：减少碎片化、减少过早/过晚课程、尽量紧凑。
- **教师满意度高**：尽量符合教师画像中的偏好与避让条件。
- **可解释**：能说明某个方案为什么较优、哪些教师满足度较低。
- **可调整**：教务可以人工修改，修改结果进入反馈闭环。

## 5. 模块三：多条件课表导出

> **状态：已落地（2026-09-06）。** 实现说明与真实数据验证见
> `docs/implementation/11-多角色课表导出.md`。四个视角（教师 / 班级 / 教室 / 教务）
> 通过 `GET /api/exports/timetable` 导出 .xlsx；导出按 `consecutive_slots` 整段展开，
> 每格写出该次课实际生效的绝对周集合，分表按教师与班级 ID 判断归属。

### 5.1 目标

导出模块负责把同一份正式课表转换成不同角色能理解、能使用的视图。

不同角色关注点不同：

| 角色 | 关注内容 | 导出形式 |
|---|---|---|
| 学生 | 自己班级每周上什么课、在哪上 | 班级课表、学生视图 |
| 教师 | 自己每周何时何地上课 | 教师课表 |
| 教务 | 全校总表、冲突检查、方案归档 | 总课表、统计表、方案报告 |
| 教室管理者 | 每个教室何时被占用 | 教室占用表 |

### 5.2 导出维度

导出能力应支持按以下条件组合：

- 学期
- 排课任务
- 排课方案
- 班级
- 教师
- 教室
- 课程
- 周次
- 星期
- 节次

### 5.3 与反馈闭环的关系

导出不是流程终点。正式课表发布后，真实使用过程中的调课、人工修改和教师反馈会重新进入教师画像与训练样本链路：

```text
正式课表 / 导出课表
  → 使用过程中的调课、修改、反馈
  → 正负样本采集
  → 教师画像更新
  → 合法候选排序模型重训
  → 下一轮排课质量提升
```

## 6. 创新点：教师画像驱动的反馈训练闭环

教师画像不是简单的展示字段，而是系统智能化的核心中间层。

### 6.1 画像来源

教师画像由多种来源融合生成：

| 来源 | 信号类型 | 示例 |
|---|---|---|
| 历史课表 | 隐式偏好 | 常上星期、常上节次、常用教室类型 |
| 正式课表 | 已接受安排 | 最终发布且长期未调整的安排 |
| 调课变动 | 负反馈或偏好修正 | 某教师频繁调走早八或晚课 |
| 教师手动填写 | 显式声明 | 避开第一节、偏好连续排课、不可用时间 |
| 教务人工调整 | 高价值反馈 | 教务把某课程从 A 时间移到 B 时间 |
| 方案选择行为 | 方案级偏好 | 教务最终选择满足度更高的方案 |

### 6.2 画像结构

画像应保留“来源”和“可信度”，避免把所有信号混成一团：

```json
{
  "teacher_id": "T001",
  "final_profile": {
    "avoid_early_period": true,
    "prefer_compact_schedule": true,
    "preferred_weekdays": [1, 3, 5],
    "max_daily_lessons": 4
  },
  "evidence": {
    "historical_schedule": {},
    "official_schedule": {},
    "adjustment_feedback": {},
    "declared_profile": {}
  },
  "confidence": {
    "avoid_early_period": 0.82,
    "prefer_compact_schedule": 0.74
  }
}
```

MVP 阶段可以先采用固定优先级：

```text
教师手动编辑 > LLM 声明解析 > 调课反馈 > 正式课表 > 历史课表
```

### 6.3 画像进入排课（当前空缺）

> **状态：未接入。** V3 时期画像通过 CP-SAT 的 objective 生效，CP-SAT 删除后，
> `scheduler/phase_scheduler.py` 不读取任何 profile —— **教师画像目前对排课结果零影响**。
> 采集、聚合、展示三层仍在，缺的是它在动态模板引擎里的作用点。这是 V3 退役留下的
> 最大空缺，也是本节从"已实现"降级为"待建设"的原因。

重新接入时必须守住的边界：

**画像只能改变顺序，不能改变可行域。** 硬约束（教师、班级、教室占用、房型、容量、
禁排、周次、连续节次）决定哪些候选合法；画像只在这批已经合法的候选里表达偏好。
任何让画像放宽硬约束的设计都会破坏第一阶段建立的课时守恒与冲突基线。

拟接入点：`phase_scheduler` 的候选枚举之后、贪心放置之前，为每个合法候选计算一个
偏好分，与现有的 `candidate_rank` / `score` 走同一条软偏好通道（该通道已存在，
目前由 LightGBM 候选占用，模型缺席时全部为 0）。

可转成偏好分的画像字段：

| 画像字段 | 偏好分含义 |
|---|---|
| 避开早课 | 第 1–2 节的候选降权 |
| 避开晚课 | 第 9–11 节的候选降权 |
| 偏好紧凑 | 与该教师当天已排片段相邻的候选升权 |
| 最大单日课时 | 超过上限的候选降权（不禁止，仅降权） |
| 偏好星期 / 节次分布 | 与历史高频位置一致的候选升权 |
| 调课负反馈 | 与被调走的位置相似的候选降权 |

权重必须可配置，且要有一条硬性回归：接入前后，任务覆盖率、硬冲突数和逐任务课时差
不得变差。满足度提升只有在这三项不退化时才成立。

输出上还需要给每个方案产出画像满足度解释明细（哪些教师满足度低、主要原因是什么），
Java 落库、前端在方案详情展示——这部分在 V3 时期做过 MVP，随 CP-SAT 一并失效。

### 6.4 正负样本闭环

系统需要把人的行为变成训练信号：

| 行为 | 样本含义 |
|---|---|
| 教务选择某个候选方案 | 该方案整体为正样本 |
| 教务放弃某个候选方案 | 该方案相对为负样本 |
| 人工把课程从 A 调到 B | A 是负样本，B 是正样本 |
| 教师申请调课并被批准 | 原安排可能违背教师真实偏好 |
| 教师长期未调整某安排 | 该安排可作为弱正样本 |

最终形成闭环：

```text
排课结果
  → 人工选择 / 修改 / 调课 / 反馈
  → 反馈事件表
  → 教师画像更新
  → 训练样本生成
  → 合法候选排序模型重训
  → 下一轮排课
```

## 9. 论文表述建议

第一阶段可以准确表述为：

> 本系统以高校合班教学任务为基本排课单元，在每天 11 个 45 分钟原子小节的时间坐标上，
> 通过绝对周次硬约束占位、完成即释放的资源回收、按周课表签名派生动态周模板、
> 全枚举合法候选加有界局部重排，生成可人工按精确周次复核、可事务发布、
> 且显式保留未排任务与课时偏差的候选课表。

不能表述的：

- 不能说模型参与了排课。第一阶段是 rules-only，LightGBM 不决定可行性也不参与候选顺序。
- 不能说教师画像影响了排课结果。画像目前不进入排课引擎（见 6.3）。
- 不能用旧的 GA / CP-SAT / 固定两阶段模板叙述描述当前实现。
- 不能用现有 LightGBM/CatBoost 产物宣称完成训练；它们的时间轴契约已失效，加载即被拒绝。

答辩时可以强调四点：

1. **不是让 LLM 直接生成课表**：核心排课由确定性规则引擎完成，模型只在第二阶段
   对已经合法的候选重排序。
2. **不是单次排课工具**：导入 → 排课 → 人工复核 → 发布 → 多角色导出是一条完整闭环，
   每一环都有验收记录。
3. **不隐藏解决不了的问题**：未排任务保留原任务身份、缺少课时和真实原因；
   硬约束问题永远不可人工豁免；可豁免项必须填写原因且草案一变就失效。
4. **口径是从真实数据里长出来的**：11 节时间轴来自学校作息说明，教学节奏来自课表网格，
   43% 的任务声明课时与课表实测不符——这些都写进了设计而不是被抹平。

可用的第一阶段实验指标（均已有产出）：

| 指标 | 来源 |
|---|---|
| 任务覆盖率 / 未排任务数 | 模拟实验台 12 场景、`phase_cover_report.json` |
| 硬冲突数（教师/班级/教室） | 排布自检与草案审计 |
| 课时守恒（逐任务与全局差值） | 课时终审、正式课表总账 |
| 待人工复核比例与原因分布 | `needs_manual_review` 明细 |
| 资源分层容量缺口 | 教室分层必要容量预检 |
| 导入成功率与五类结果分布 | `import_batch` 台账 |
| 导入数据质量：声明课时与实测不符比例 | 212 条真实任务中 92 条（43%） |
